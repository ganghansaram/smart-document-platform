## 2. 산업 표준 벤치마크 (튜토리얼·매뉴얼 패턴)

| 도구 | 차용 가능한 패턴 | 적용 방식 |

| **Linear Method** | 짧은 챕터 + "왜 이게 중요한가" 박스 | 각 기능 첫 줄에 비즈니스 가치 배치 |

| **Turnitin Guide** | 5단계 신호등 + 분기형 의사결정 가이드 | "노란색 → 어떻게 대응?" Yes/No 분기 |

| **MDN Web Docs** | "Learn / Reference / Cookbook" 3구분 | 문서 상단에 모드 전환 탭 (선택) |
| **Intercom Articles** | 인라인 주의/팁/경고 박스 | 💡 / ⚠️ / 📌 callout 3종 |
| **Acrolinx Help** | 점수 기준 + 실제 검출 사례 | 임계값 옆에 실제 텍스트 사례 배치 |

### 차용 우선순위 (현 프로젝트 적합도)
1. ⭐⭐⭐ **Copyleaks 실제 문장 비교 카드** — 가장 큰 학습 효율 향상
2. ⭐⭐⭐ **Stripe 5분 시작 박스** — 진입로 해결
3. ⭐⭐⭐ **GitHub 주석 스크린샷** — UI 학습 효율
4. ⭐⭐ **Turnitin 분기형 가이드** — FAQ 능동 진단화
5. ⭐⭐ **Linear "왜 이게 중요한가" 박스** — 비즈니스 가치 선행
6. ⭐ **MDN 3구분 탭** — 보류 (단일 문서 유지가 SSOT 원칙에 더 부합)

## 3. 적용 패턴 카탈로그 (Phase 1 신설 5종)

### A. **5분 시작하기 박스** (`.po-quickstart`)
- 상단 hero 직후 배치, 5스텝 (50줄 이내)
- 각 스텝: 한 줄 액션 + 작은 스크린샷 + 예상 결과
- 예: ① 검증 페이지 진입 → ② 유사도 모드 선택 → ③ 문서 2개 업로드 → ④ "검사 시작" 클릭 → ⑤ 결과 카드 1개 클릭 → 본문 하이라이트 확인

### B. **시나리오 카드** (`.po-scenario-card`)
- 기능 헤딩을 "일감"으로 재구성
- 3개 후보 (사용자 결정 시트 §6 참조)
- 각 카드: 시나리오 제목 + 상황 1~2줄 + 5스텝 walkthrough + "결과 해석 팁"
- 기존 "유사도 검사" h2 헤딩 자리에 시나리오 3개 배치

### C. **글로서리 비교 카드** (`.po-glossary-row`)
- "동일 vs 거의 동일 vs 의역 vs 약한 유사" 4열 비교
- 각 열: 카테고리 라벨 + 색상 점 + **실제 영문/한글 문장 예시 1쌍** + 임계값 한 줄
- 표 대체 — 표는 정의만, 카드는 직관 인지
- SSOT 원칙: 라벨은 `data/help/similarity-help.json` 경유 (Plan-45 규칙 §1)

### D. **주석 스크린샷** (`.po-hotspot-image`)
- 기존 스크린샷에 ①~⑥ 번호 핫스팟 absolute 오버레이
- 호버 시 툴팁 — 해당 영역 설명 + "→ 자세히" 앵커 링크
- 정적 이미지 → 인터랙티브 학습 자료로 격상
- CSS만으로 구현 (`position:absolute` + `:hover`), JS 없음

### E. **분기형 진단 박스** (`.po-decision-tree`)
- FAQ 7건 → 진단 트리 3~4개로 재편
- 예: "내 점수가 노란색이다 → 인용 표시 했나? Yes/No → 권장 액션"
- `<details>` 중첩으로 JS 없이 구현

### 보조 패턴 (기존 컴포넌트 활용)
- **콜아웃 3종** (`.po-callout` 변형) — 💡 팁 / ⚠️ 주의 / 📌 핵심 (배경색·아이콘만 다름)
- **"왜 이게 중요한가" 박스** — `.po-callout.po-why` 변형 (좌측 4px accent border)

### 디자인 원칙
1. **하드코딩 금지** — 색상·간격·둥글기·트랜지션 모두 tokens.css 변수
2. **다크모드 자동** — CSS 변수 의존, 별도 `.dark` 셀렉터 X (이미 토큰이 다크 분기)
3. **인쇄 안전** — `@media print { .po-hotspot-tip { display: none } }` (호버 툴팁 인쇄 시 깨짐 방지)
4. **Vanilla 가능 영역만** — 핫스팟 툴팁은 CSS `:hover`만, JS 없음. 진단 트리는 `<details>`만
5. **반응형** — `.po-glossary-row` 768px 이하 1열로 wrap, `.po-quickstart` 5스텝은 모바일 세로 스택

| **③** | **회람·승인용 PDF 보고서 만들기** | 검토자·관리자 | 중 (단계별) | 검사 결과를 검토 회람·승인 라인이 즉시 이해 가능한 PDF로 산출 (결과지·매칭 상세·검사 기준 3페이지) |

→ 후보 ④⑤⑥ (외부 표준서 차용 측정·여러 버전 비교·다국어) 은 **Phase 2 후 검토**.

### 6-2. 글로서리 비교 카드 — ✅ 확정 (기술 문서 도메인)

사내 기술 문서에서 흔한 패턴(국방/항공우주 도메인 어휘 포함)에 맞춰 동일 베이스 문장을 4단계로 변형.

| 카테고리 | 검사문서 (작성 중인 문서) | 비교문서 (사내 기존·외부 공개 문서) | 색상 |
|----------|-----------------------|----------------------------|------|
| **동일** | The contractor shall provide all test equipment required for environmental qualification testing. | The contractor shall provide all test equipment required for environmental qualification testing. | 🔴 빨강 |
| **거의 동일** | The contractor shall provide all test equipment required for environmental qualification testing. | The supplier shall furnish all test equipment necessary for environmental qualification testing. | 🟧 연빨강 |
| **의역** | The contractor shall provide all test equipment required for environmental qualification testing. | 환경시험 수행에 필요한 모든 시험 장비는 계약자가 공급한다. | 🟪 보라 |
| **약한 유사** | The contractor shall provide all test equipment required for environmental qualification testing. | Test equipment for qualification activities is the responsibility of the program. | ⚪ 회색 |

→ 영문 베이스 + 한↔영 의역 1건으로 한국어 사용자도 바로 인지. 정형구문(`the contractor shall`)이 들어 있어 "이건 자동 제외되는 거 아닌가?" 같은 후속 학습으로 자연 연결.

### 6-5. 톤 — ✅ 확정 (사내 엔지니어 톤)

- **존댓말 유지** (`~합니다`, `~합니다`) — 기존 가이드 일관성
- **마케팅 어휘 금지** — "혁신", "최첨단", "강력한", "직관적인" 등 사용 금지

- **단정적 어휘 우선** — "권장합니다" 보다 "이렇게 합니다"·"이 경우 X 입니다"
- **출처 명시** — 산식·임계값은 "Copyleaks 기준", "Turnitin 기준" 처럼 근거 출처 인라인 (사내 엔지니어가 신뢰하려면 출처 필요)
