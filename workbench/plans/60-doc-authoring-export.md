## 0. 한 줄 요약

**워드 등 기존 문서 문화는 유지하되, "통일 양식"을 웹 편집기에 반영해 작성·관리하고, 내보내기로 DOCX 출력→다듬어→제출하는 협업 저작 공간을 만든다.**
- **(A) 저작**: 일반 엔지니어가 **마크다운↔WYSIWYG(드롭인 편집기)** 로 새 문서를 쉽게 작성, `.md`(SSOT) 저장. 기존 변환 웹북(복잡 HTML)은 Monaco 유지로 안전 보존.
- **(B) 내보내기·양식**: 마크다운 SSOT → **Pandoc + `reference.docx`(통일 양식 1벌)** → DOCX. 충실도 한계는 "워드 다듬기" 단계로 흡수(업계 표준 docs-as-code 흐름).
- **동시 편집**: **soft lock(presence + 낙관적 저장 검사) + 담당자 소유권(소유자 1인·편집권·위임)** 으로 손실 방지 + 책임 명확화.
- **공통 계약**: A·B 를 잇는 **"통일 양식 사양·콘텐츠 모델"** 은 Phase 1 에서 먼저 확정(이게 둘의 강결합 지점).

## 2. 핵심 갈림길 — 콘텐츠 모델 (의사결정 #1)

> 이 한 가지가 후보 선택·통합 난이도·리스크 전부를 좌우한다. 다른 모든 논의의 전제.

현재 Explorer 콘텐츠는 **변환 파이프라인이 생성한 복잡 HTML** 이다:
- 표: `rowspan`/`colspan` 병합 (python-docx raw XML 순회로 정밀 변환)
- 수식: **MathML** (OMML→MathML, 브라우저 네이티브 렌더)
- provenance 주석(`<!-- converter: ... -->`), 장절번호·캡션 합성 구조
- 검색 인덱스·RAG 파이프라인이 이 HTML 구조에 의존

**어떤 WYSIWYG 도 이 HTML 을 무손실 왕복(round-trip)하지 못한다.**
- 마크다운 기반(Toast UI): 저장 시 마크다운으로 직렬화 → **병합 표·MathML 소실**
- 자체 스키마형(TinyMCE/CKEditor): 미지의 노드(MathML, custom attr) **정규화 과정에서 제거·왜곡**

→ 그러므로 선택은 둘 중 하나다:

| 방향 | 정의 | 콘텐츠 | 위험 |
|------|------|--------|------|
| **A. 신규 작성 경로** | 일반 엔지니어가 **새 문서**를 마크다운/WYSIWYG 로 작성 | **마크다운(.md)** 신규 저장 | 콘텐츠 포맷 이원화(HTML+MD) → 서빙·검색·RAG 변환 비용 |
| **B. 기존 HTML 비주얼 편집** | 같은 HTML 을 Monaco(소스)↔WYSIWYG(시각) 토글 | **HTML 단일** 유지 | 복잡 문서 무손실 왕복 불가 → "안전 문서"로 제한 필요 + 라이선스 마찰 |

**제안: 방향 A 를 1차 목표로.** 사용자의 진짜 의도("일반 엔지니어가 새 문서를 쉽게 작성")는
기존 학술 변환 웹북을 비주얼로 고치는 게 아니라 **신규 저작 진입장벽을 낮추는 것**이다.
기존 변환 웹북은 Monaco(파워유저) 유지가 안전하다. (상세 §6)

### 2026 트렌드 재검증 — 제약이 결정한다 (의사결정 #2)
- **요즘 대세**: 블록형(Notion) + ProseMirror/Lexical 헤드리스 + Yjs 협업 → **TipTap·Milkdown/Crepe·BlockNote·Lexical**
- 품질·미래성은 이들이 Toast UI 보다 앞섬. **그러나 전부 우리 제약에 탈락**:
  - TipTap: standalone UMD 번들 없음, ES모듈+esm.sh 방식 → 폐쇄망엔 번들러 필요. Milkdown/Crepe·Lexical 동일. BlockNote=React(무프레임워크 위반)
- **드롭인 번들(=Monaco처럼 벤더링)을 그냥 주는 모던 옵션 = Toast UI(마크다운+WYSIWYG), Editor.js(블록 JSON) 둘뿐**
- **Editor.js 격상**: 블록 UX 가 일반 사용자에 더 친숙(트렌드 부합)하나, **출력이 블록 JSON** → 서빙·검색·RAG 통합 마찰 최대, 표·수식 약함, 블록별 플러그인 다발 벤더링

  - 이 완화를 허용하면 **TipTap·Milkdown/Crepe 후보 개방**. 차이: Toast UI/Editor.js 는 기성 번들 수령(업그레이드 마찰 0), TipTap/Milkdown 은 우리가 1회 조립+유지

## 4. 다각도 평가 (코드 · UI/UX · 웹디자인 · 사용자)

### 🧑‍💻 코드 전문가
- **EditorCore 어댑터는 Monaco 전제** — Toast UI 는 Monaco 언어 교체가 아니라 **별도 풀 에디터**.
  → "EditorCore 어댑터 추가"가 아니라 **EditorCore 와 동급의 2번째 편집기 엔진**을 모달 안에 끼우는 작업.
  분할 뷰·모달·저장 훅 인프라는 재사용하되, 엔진 추상화 1단계 더 필요.
- 무빌드 제약이 TipTap 을 즉시 탈락시킴 → 후보가 Toast UI / Quill / (HTML이면)TinyMCE 로 좁혀짐.
- 콘텐츠 이원화(HTML+MD)는 **검색 인덱스·RAG·서빙 전 경로**에 영향 → MD→HTML 렌더 일관성이 숨은 핵심 작업.
- **가역성**: 기존 Monaco 경로 100% 유지 + 신규 경로 추가 → 롤백 안전. ✅

### 🎨 UI/UX 전문가
- "모드 스위치" 자체가 정답 패턴 — **신규 사용자는 WYSIWYG, 파워유저는 소스**, 같은 문서를 두 시야로.
- Toast UI 의 탭 토글 = 학습 비용 거의 0. 마크다운 단축키도 흡수해 "키보드 파워유저"도 만족.
- 주의: **모드 전환 시 데이터 손실 경고** UX 필수(복잡 HTML→MD 변환 불가 문서는 토글 비활성).
- 우리 디자인 토큰(`--active-color` 블루 통일)과 Toast UI 기본 테마의 **시각 충돌** → CSS 토큰 오버라이드 레이어 필요.

### 🖌️ 웹디자인 전문가
- Toast UI 기본 스킨은 모던하나 **우리 플랫폼 헤더·모달 시스템과 톤 통일** 작업 필요(`tokens.css` 변수 매핑).
- 다크모드: Toast UI 다크 테마 존재 → 우리 다크 토큰과 브리지. 하드코딩 색 금지 규칙 준수해야.
- 작성 공간은 넓을수록 쾌적 → 단, 전용 페이지 신설 대신 **기존 모달의 풀스크린 상태**로 충족(현 모달에 풀스크린 토글 내장). 동일 작업 단일 공간 모델 유지 (§6 확정).

### 👤 사용자(일반 엔지니어)
- "HTML 안 만지고 글 쓰고 표·이미지·코드블록 넣고 공유" = 정확히 충족.
- 마크다운은 엔지니어 친화적(Git/README 문화) + WYSIWYG 는 비개발 직군 포용 → **두 직군 동시 만족**.
- 공유: 작성→웹북 뷰로 즉시 공개되는 흐름이 자연스러움.

## 6-A. 동시 편집·충돌 대비 (업계 관행) — **신규 보강**

### 현재 상태 (사실 확인 · 2026-06-15)
- `backend/api/document.py` `save_document` = **권한체크 → 백업 → 파일 덮어쓰기**가 전부.
- **버전/ETag/잠금/ mtime 검사 전무 = last-write-wins.** 두 편집자가 같은 문서 저장 시 **뒤 저장이 앞 저장을 조용히 덮음.** 복구는 `backups/` 타임스탬프 백업뿐.
- 현재는 "주로 1인 편집" 전제라 표면화 안 됐을 뿐 → **공유 문서 공간 전환 시 실데이터 손실 리스크.**

### 업계 관행 (가벼움 → 무거움)
1. **낙관적 잠금(ETag/If-Match → 412/409)** — 웹 표준. GET 시 버전 토큰 반환 → 저장 시 동봉 → 서버가 stale write 거부. (강제 잠금은 웹에서 비현실적: 방치 락)
2. **편집 중 표시(soft lock/presence)** — heartbeat 기반 "○○님 편집 중" 배너. 경고용(강제X).
3. **자동저장 + 버전 이력** — 주기 draft 저장 + 스냅샷/복원. 충돌 전략과 무관하게 손실 감소.
4. **실시간 협업(CRDT/Yjs)** — 동기화 서버·웹소켓 필요 → **폐쇄망 v1 제외(과설계).**

### 채택 결정 (2026-06-15 → 2026-06-16 재정정) — Soft Lock + 담당자 소유권 레이어
> 변경 이력: 6/15 "배타 잠금+담당자+위임" 확정 → 6/16 soft lock 으로 경량화(담당자 제외) → **6/16 재정정: 담당자 소유권 복원**.
> 사유: **AAM 양사 공동 저작 맥락(현대차-자사) 확인**으로 "문서별 책임자 지정"이 실수요임이 드러남(실시간 협업·망 연계는 없음 → 단순 데이터 손실 방지 가정이 깨짐). → soft lock(동시저장 방어)에 **담당자 소유권(책임·편집권)** 레이어를 더한다. 둘은 목적이 달라 양립.

**(1) 동시저장 방어 = Soft Lock (2겹 안전망)**
- 순수 비관적 잠금(체크아웃)은 과설계, 순수 낙관적 잠금은 "공들인 작업 저장 거부" 약점 → **둘의 중간인 soft lock**.
  1. **예방 — 편집 중 표시 (presence)**: heartbeat 기반 "○○님 편집 중" 배너. **강제 차단 아님(신호등)** → 충돌 전 인지하여 회피.
  2. **복구 — 낙관적 저장 검사 (ETag/버전)**: GET 시 버전 토큰 반환 → 저장 시 동봉 → stale write 감지 시 **409/412**. 거부돼도 **작업 보존**, 선택지 제공: ① 비교·합치기 ② 사본 저장 ③ 확인 후 덮어쓰기(백업 존재). → 작업 폐기 강요 금지.

**(2) 소유권 레이어 (복원, 2026-06-16) — 소유자 1인 + 편집권 + 위임**
- **소유자(담당자)**: 문서별 책임자 **1인**. **편집권 = 소유자에 한정**(소유자만 편집 버튼 노출). 타인은 열람.
- **위임(handoff)**: 소유자가 다른 사용자에게 편집권·책임을 **이양**(소유자 변경).
- **관리자 재지정**: 소유자 부재(인사이동·이탈) 시 **admin 이 소유자 재지정**.
- soft lock 과의 관계: 소유권 = "누가 편집하는가"(권한), soft lock = "동시 저장 충돌 방지"(안전). 소유자가 여러 기기/세션으로 같은 문서를 열어도 soft lock 이 백스톱.
- **방치 락 문제 없음**: 소유권은 세션 락이 아닌 **영속 속성** → 무활동 자동 해제 불필요(관리자 재지정으로 충분).

**(3) 여전히 불채택 (무거운 장치)**
- 배타적 잠금/문서 체크아웃 · 무활동 자동 해제 타이머 · **실시간 협업(CRDT/Yjs)** — 실시간·망 연계 없음 → 과설계.

**(4) 상태 저장 (폐쇄망·단일 프로세스·저경합)**
- presence = **인메모리 heartbeat**(재시작 시 자연 만료), 버전 토큰 = **파일 mtime/해시**, 소유자 = **문서 메타(파일 사이드카 또는 인덱스)에 영속**. 분산 락(Redis/ZooKeeper) **불필요**.
- 보조(선택): 자동저장/로컬 draft 병용 가능.

### 소급 적용
- 동시수정 갭(last-write-wins)은 **기존 Explorer(Monaco/HTML)에도 현존** → soft lock 을 신규/기존 양쪽 공통 적용 가치.
- 버전 검사는 기존 `save_document` 에 **`If-Match` 헤더 검사만 추가**하면 소급 가능(경량) — 별도 잠금 인프라 불요.

## 6-C. 통일 양식 + DOCX 내보내기 (B축) — **통합 신설 (조사 2026-06-16)**
> 상세 근거·출처: `workbench/reports/doc-authoring-export-research-2026-06-16.md` (deep-research, 22소스·25주장 교차검증)

### 컨셉
- 워드 등 **기존 문서 문화 유지**. 웹에서 **통일 양식으로 작성/관리 → 내보내기로 DOCX 출력 → 워드에서 다듬어 제출**.
- 마크다운 **단일 원본(SSOT)** → 다중 출력(웹 HTML 서빙 + DOCX 제출본). 업계 표준 **docs-as-code / single-source authoring**.

### 검증된 방식 — Pandoc + reference.docx (공식 MANUAL 교차검증)
- `pandoc in.md -o out.docx --reference-doc=회사양식.docx` → 참조 문서의 **스타일·여백·머리글/바닥글을 일괄 적용**(본문 내용은 무시). **통일 양식을 reference.docx 한 벌로 관리**.
- Pandoc = **정적 단일 바이너리**, 1회 다운로드 후 오프라인 동작, Win/Linux, GPL → **폐쇄망 적합**. 백엔드(FastAPI)에 동봉, subprocess 호출(별도 실행파일이라 GPL 비전염).
- `custom-style`(div=단락/span=문자)로 내장 매핑 넘는 스타일 적용 가능 — 단 **스타일명 매칭 기반**.

### 한계 → "다듬기 단계" 필수 (사용자 컨셉과 일치)
- **병합표(rowspan/colspan)·복합 수식·표지/목차는 완전 충실하지 않음.** → 내보내기를 최종 제출본으로 보지 말 것.
- 우리 **Converter(OMML→MathML·표 병합) 노하우로 후처리 보강 가능성** → Phase 1 PoC 에서 충실도·공수 정량화.

### 비채택 (조사 근거)
- **Notion식 블록 모델**: 마크다운이 native 저장 아닌 **lossy 내보내기** → 우리 마크다운 SSOT 확정과 충돌.
- **DITA/Schematron 풀 스키마 강제**: 중량급 XML 저작·무빌드 위배 → **템플릿 골격 프리필 + 경량 누락 경고** 수준만 차용.

### 아키텍처
```
[Toast UI 마크다운 저작] (통일 양식 템플릿 프리필)
  → .md (SSOT, contents/ "작성 문서" 폴더)
  ├ 웹 서빙: marked + DOMPurify → HTML  (Plan-60 A축, 기존 파이프라인)
  └ 내보내기: POST /api/export → Pandoc --reference-doc=양식.docx → DOCX
                                 → 사용자가 워드에서 다듬어 제출
- 통일 양식 = data/ 에 reference.docx 한 벌 버전관리 + 편집기 템플릿 골격(쌍을 1개 사양으로 설계)
```

### 확정된 결정 (2026-06-15~16)
- ✅ 방향 **A** (신규 MD 작성 경로) · **무빌드 고수** · 콘텐츠 이원화(HTML 웹북 + MD 신규) 수용
- ✅ **동시편집 (2026-06-16 재정정)**: **soft lock(편집 중 표시 + 낙관적 저장 검사) + 담당자 소유권 레이어(소유자 1인 + 편집권 + 위임, 관리자 재지정)**. AAM 양사 공동 저작 맥락으로 담당자 복원, 단 배타 잠금·실시간 협업은 불채택. (§6-A)
- ✅ **편집기 / TipTap 재검토 (2026-06-16)**: **TipTap 불채택.** 재검토 사유 = AAM 공동 저작 검토(현대차-자사). 그러나 **실시간 동시 편집 없음 + 양사 망 연계 비현실** 확인 → TipTap 의 결정적 강점(TipTap+Yjs 실시간 협업)이 무용, 헤드리스 "UI 전부 자작·유지" 부담만 남아 비용 대비 부적합. → **드롭인 마크다운 편집기 유지**. 최종 후보 = **Toast UI**(드롭인, 단 노후) 또는 **Milkdown Crepe**(유지보수 중, 1회 빌드 필요) — Phase 1 착수 전 택1.
  - AAM 양사 공유 방식(망 연계 없이 문서 교환·관리)은 Plan-60 범위 밖 → **별도 전략 계획으로 분리**.
- ✅ **진입 위치 (2026-06-15)**: **공통 모달 단일안** — 전용 풀스크린 페이지 신설 안 함. 기존 `editor-modal` 셸 재사용, 신규 저작 시 풀스크린 상태 기본. (사유: 동일 작업 단일 공간 모델 = 일관성 + 모달 인프라 재사용, §6)
- ✅ **공유 모델 (2026-06-16)**: **v1 최소형** — 신규 MD 도 기존 `contents/` 단일 공유 공간에 저장, 전역 RBAC(viewer/editor/admin) 그대로. **문서별·사용자별 권한/비공개 개념 신설 안 함.** (현 플랫폼에 접근제어 자체가 없음 → YAGNI)
  - **메뉴 배치 = (가) admin 큐레이션**: 신규 문서는 `contents/` 의 **전용 "작성 문서" 폴더**에 모이고, 좌측 메뉴 트리(`data/menu.json`) 편입은 **admin 권한 유지**(현 `menu.py` = `require_admin` 규칙 불변). editor 는 트리 직접 수정 불가 → drafts→published 흐름.
- ✅ **잠금 소급 범위 (2026-06-16)**: **기존 Explorer 에도 소급** — soft lock(presence + If-Match)을 신규 MD/기존 Monaco·HTML **공통 적용**. 공통 모달 셸 공유 + `save_document` 단일 진입 덕에 한 번 추가로 양쪽 커버(신규에만 적용은 오히려 분기 추가). 기존 last-write-wins 갭도 동시 해소.
- ✅ **MD 저장 경로 (2026-06-16, 코드 검증)**: 현 `save_document` 는 **파일 미존재 시 404(생성 불가) + `prettify_html` 강제(MD 손상)** → 신규 MD 는 **신규 엔드포인트**(`POST /api/documents` 생성 + MD-safe 저장). HTML 웹북 `save_document` 는 불변. 위치 = `contents/` "작성 문서" 폴더.
- ✅ **내보내기·양식 (2026-06-16, 조사)**: 마크다운 SSOT → **Pandoc + `reference.docx`(통일 양식 1벌) → DOCX**, Pandoc 정적 바이너리 백엔드 동봉(폐쇄망). "내보내고 워드 다듬어 제출" 흐름. Notion 블록·DITA 강제 비채택. (§6-C)
- ✅ **통합 (2026-06-16)**: 구 "Explorer WYSIWYG 편집기"(저작)와 "통일 양식·DOCX 내보내기"(조사)를 **본 계획 하나로 통합** — 공통 계약(통일 양식·콘텐츠 모델) 강결합 때문.

## 8. 단계 제안 (통합 후 재편 — 상세 체크는 상단 트래커)
- **Phase 0 (완료)**: 편집기 드롭인 PoC — 폐쇄망 토글·`.md` 직렬화 검증 ✓
- **Phase 1【공통 계약·최우선】**: 대표문서 코퍼스·베이스라인 + **Pandoc/reference.docx 충실도 PoC** + **통일 양식 사양 정의** + 편집기 최종 택1. → 콘텐츠 모델 확정(Phase 2·3 입력)
- **Phase 2 (A 저작)**: `EditorEngine` 레이어 + 공통 모달 + 양식 템플릿 프리필 + `.md` 저장/서빙 + soft lock + 담당자 소유권
- **Phase 3 (B 내보내기)**: 백엔드 Pandoc 동봉 + `/api/export` + reference.docx 통일 양식 + custom-style 후처리
- **Phase 4 (마무리)**: "작성 문서" 폴더·admin 메뉴 편입, 사용자 테스트, Monaco 경로 회귀 검증
