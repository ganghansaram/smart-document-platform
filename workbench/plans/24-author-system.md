> **작성일**: 2026-04-01
> **상태**: 설계 논의 (구현 미착수)
> **선행**: Plan-23 (Verify 고도화) Phase 1~2 완료 후 착수 권장

## 1. 배경 및 동기

### 1.1 문제 정의

사내 스펙 문서 대부분이 외부 영문 원문(MIL-STD, AS, EN 등)을 참조하여 작성되어 왔다. "우리 회사만의 스펙"을 제정하려면:

1. 유사한 원문 스펙 3~5개를 **나란히 놓고 비교**해야 한다
2. 어떤 내용이 **공통**이고, 어떤 내용이 **특정 문서에만** 있는지 파악해야 한다
3. 채택할 항목을 **사람이 선별**하여 판단해야 한다
4. 선별 결과를 기반으로 **우리 스펙 초안을 생성**해야 한다
5. 생성된 초안이 원문과 **표절 문제가 없는지 검증**해야 한다

현재 이 전 과정이 **엑셀 수작업**으로 수행되고 있다. 3~5개 문서를 비교 테이블로 정리하는 데만 수 시간이 소요된다.

### 1.2 시장 공백

| 기존 도구 | 하는 것 | 못 하는 것 |
|-----------|--------|-----------|
| IBM DOORS, Polarion | 요구사항 추적/관리 | 다중 문서 합성/생성 |
| 카피킬러, Turnitin | 유사도 검출 | 문서 생성 |
| ChatGPT, NotebookLM | 단일 문서 요약 | 구조화된 다중 문서 비교 합성 |
| Covidence (학술 리뷰) | 체계적 리뷰 프로세스 | 기술문서 도메인, 폐쇄망 |

**"구조화된 문서 합성(Structured Document Synthesis)"은 현재 모든 도구가 수작업에 의존하는 영역.**

### 1.3 플랫폼 내 위치

```
┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│ Explorer │  │ Notebook │  │  Verify  │  │  Author  │
│          │  │          │  │          │  │          │
│ 조직 문서 │  │ 개인 문서 │  │ 문서 품질 │  │ 문서 합성 │
│ 탐색·검색 │  │ 번역·분석 │  │ 비교·검증 │  │ 분석·생성 │
│ AI 질의  │  │ 지식 관리 │  │ 유사도   │  │ 템플릿   │
└──────────┘  └──────────┘  └──────────┘  └──────────┘
  소비(읽기)    내재화(이해)    검증(판단)     생산(창작)
```

**Author = "생산(창작)"** — 여러 소스 문서를 분석하고, 사람의 판단을 거쳐, 새로운 문서를 만드는 시스템.

## 2. 핵심 워크플로우

### 2.1 전체 흐름 (6단계)

```
[1] 소스 문서 투입
    MIL-STD-810G, AS9100, 사내 기존 스펙 등 2~5개 업로드
    (DOCX/PDF 업로드 또는 Notebook에서 가져오기)
        ↓
[2] 구조화 추출 (AI + 분석 템플릿)
    각 문서에서 요구사항/조건/수치를 AI가 추출
    → 분석 템플릿(테이블)의 행으로 배치
        ↓
[3] 비교 매트릭스 (자동 분류)
    ┌──────────────┬──────────┬──────────┬──────────┐
    │ 항목          │ MIL-810G │ AS9100   │ 사내 현행 │
    ├──────────────┼──────────┼──────────┼──────────┤
    │ 진동 시험 조건 │ 10~2000Hz│ 10~2000Hz│ 10~500Hz │ ← 부분 공통
    │ 온도 범위     │ -54~71°C │ -40~85°C │ 없음     │ ← 충돌
    │ 습도 요구     │ 95% RH   │ 95% RH   │ 95% RH   │ ← 전체 공통
    │ EMI 차폐     │ 40dB    │ 없음     │ 30dB    │ ← 부분 공통
    └──────────────┴──────────┴──────────┴──────────┘

    색상 분류:
    - 초록: 전체 공통 (모든 문서 동일/유사)
    - 노랑: 부분 공통 (일부 문서만 포함, 내용 유사)
    - 빨강: 충돌 (문서 간 수치/내용 상이)
    - 회색: 단일 문서만 (특정 문서 고유 항목)
        ↓
[4] 검토 + 선별 (사람이 판단)
    각 행에 대해:
    ☑/☐ 채택 체크박스
    드롭다운: 어느 문서의 값을 채택할지 선택
    메모: 판단 근거 기록
    편집: 값을 직접 수정

    예시:
    ☑ 진동: MIL-810G 기준 채택 (10~2000Hz)
       메모: "KF-21 시험 이력 근거, 사내 현행 범위는 부족"
    ☑ 온도: AS9100 범위 채택 (-40~85°C)
       메모: "MIL 범위는 극한 환경 과도, AS9100이 적절"
    ☐ 습도: 공통이므로 자동 포함
    ☑ EMI: MIL 기준 채택 (40dB), 사내 기준 상향
       메모: "30dB → 40dB 상향, EMC 팀 협의 완료"
        ↓
[5] 초안 생성 (AI + 선별 결과)
    체크된 항목 + 채택 값 + 메모 → LLM 프롬프트
    → Markdown 형식의 스펙 초안 생성
    → Monaco 편집기에서 검토/수정
        ↓
[6] 검증 연계 + 최종 산출
    → Verify로 보내기: 유사도 검사 (원문 표절 점검)
    → Verify로 보내기: 규칙 검증 (작성 지침 준수)
    → 피드백 반영 후 최종 Markdown 다운로드
```

### 2.2 사용자 여정 시나리오

> **시나리오**: 진동 시험 규격 제정
>
> 김 엔지니어는 KAI 진동 시험 표준을 만들어야 한다.
> MIL-STD-810G, RTCA DO-160G, 사내 현행 규격 3개를 참조해야 한다.
>
> 1. Author에서 프로젝트 생성, 3개 문서 업로드
> 2. AI가 각 문서에서 "시험 조건, 합격 기준, 적용 범위" 추출
> 3. 비교 테이블에서 한눈에 차이점 확인
> 4. 각 항목별로 어느 기준을 채택할지 체크하며 메모
> 5. [초안 생성] → KAI 양식의 Markdown 스펙 초안
> 6. Verify에서 원문 대비 유사도 검사 → 문제 구간 수정
> 7. 최종 Markdown 다운로드
>
> **기존**: 엑셀 비교표 3시간 + 워드 초안 2시간 = **5시간**
> **Author**: 업로드~검토 30분 + 초안 수정 30분 = **1시간**

## 3. 화면 구성

### 3.1 전체 레이아웃

```
┌─ 플랫폼 헤더 ───────────────────────────────────────────────┐
├─ 프로젝트 목록 ─────────────────────────────────────────────┤
│  [+ 새 프로젝트]  [프로젝트 A] [프로젝트 B] ...              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ┌─ 좌측: 소스 문서 패널 ──┐  ┌─ 우측: 분석 워크벤치 ────┐   │
│  │                        │  │                          │   │
│  │  📄 MIL-STD-810G       │  │  [추출] [매트릭스] [초안]  │   │
│  │  📄 AS9100             │  │                          │   │
│  │  📄 사내 현행           │  │  (탭별 뷰 전환)           │   │
│  │                        │  │                          │   │
│  │  [+ 문서 추가]          │  │  비교 테이블 / 편집기     │   │
│  │  [Notebook에서 가져오기] │  │                          │   │
│  └────────────────────────┘  └──────────────────────────┘   │
│                                                             │
│  ┌─ 하단: 액션 바 ─────────────────────────────────────────┐ │
│  │  [초안 생성] [Verify로 보내기] [Markdown 다운로드]        │ │
│  └─────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 분석 워크벤치 탭

**탭 1: 구조화 추출 뷰**
- 각 소스 문서의 추출 결과를 문서별 컬럼으로 표시
- AI가 추출한 항목 확인/수정 가능
- 추출 항목: 요구사항, 수치 조건, 적용 범위, 시험 방법 등

**탭 2: 비교 매트릭스**
- 핵심 뷰. 모든 문서의 항목을 행 기준으로 정렬
- 색상 코딩: 초록(공통) / 노랑(부분) / 빨강(충돌) / 회색(단일)
- 각 행: 체크박스 + 채택 드롭다운 + 메모 입력
- 필터: 공통만 / 충돌만 / 미결정만

**탭 3: 초안 편집기**
- Monaco 편집기 (editor-core.js 재사용)
- 생성된 Markdown 초안 직접 편집
- 분할뷰: 좌=편집, 우=미리보기 (Notebook 편집기 패턴 그대로)

### 3.3 프로젝트 개념

Author는 **프로젝트 단위**로 작업을 관리한다 (Compare의 휘발성과 다름):

- 프로젝트 = 소스 문서들 + 추출 결과 + 비교 매트릭스 + 선별 상태 + 초안
- 이유: 문서 합성은 1회 세션으로 끝나지 않음. 며칠에 걸쳐 검토/수정하는 작업
- 저장: `data/author/{username}/{project_id}/`
  - `meta.json` — 프로젝트 메타 (이름, 생성일, 상태)
  - `sources/` — 업로드된 소스 문서
  - `extraction.json` — AI 추출 결과
  - `matrix.json` — 비교 매트릭스 + 선별 상태 + 메모
  - `draft.md` — 생성된 초안

## 4. 기술 설계

### 4.1 구조화 추출 (AI)

**입력**: 소스 문서 텍스트 (DOCX/PDF → 텍스트 추출, 기존 인프라 재활용)

**추출 전략**: Ollama 구조화 출력 (JSON Schema)

```
프롬프트:
"다음 기술문서에서 요구사항을 추출하세요.
 각 요구사항에 대해 다음을 식별:
 - category: 항목 분류 (시험조건, 성능요구, 재료요구, 환경조건, ...)
 - subject: 항목명 (진동 시험, 온도 범위, ...)
 - requirement_text: 원문 요구사항 문장
 - values: 수치/조건 (있으면)
 - requirement_level: shall/should/may/info"
```

**배치 처리**: 문서가 길면 섹션 단위로 분할 호출, 결과 병합

### 4.2 비교 매트릭스 생성

**항목 매칭**: 서로 다른 문서에서 추출된 항목을 "같은 주제"끼리 매칭

- 1차: `subject` 필드 텍스트 유사도 (bge-m3 임베딩, 크로스링구얼)
- 2차: `category` 일치 여부로 보정
- 3차: 사용자 수동 매칭/분리 (AI가 놓친 것 보정)

**분류 로직**:
```
전체 공통: 모든 문서에 매칭 항목 존재 + 값 유사도 ≥ 0.85
부분 공통: 2개 이상 문서에 매칭 + 값 유사
충돌:     2개 이상 문서에 매칭 + 값 상이 (유사도 < 0.70)
단일:     1개 문서에만 존재
```

### 4.3 초안 생성 (AI)

**입력**: 선별된 항목 (체크박스 ON) + 채택 값 + 메모

**프롬프트 구조**:
```
"다음 요구사항 항목들을 기반으로 기술 규격서 초안을 작성하세요.

형식: Markdown
구조: 1. 적용 범위 → 2. 참조 문서 → 3. 요구사항 → 4. 시험 방법

채택된 항목:
[항목 1] 진동 시험 조건: 10~2000Hz (출처: MIL-STD-810G)
  - 메모: KF-21 시험 이력 근거
[항목 2] 온도 범위: -40~85°C (출처: AS9100)
  - 메모: MIL 범위는 과도
..."
```

**출력**: Markdown 초안 → `draft.md`

### 4.4 Verify 연계

Author에서 [Verify로 보내기] 클릭 시:
- 초안 텍스트 + 소스 문서들을 Verify 유사도 검사 API로 전달
- Verify가 유사 구간 식별 → 결과를 Author에서 표시
- 구현: URL 파라미터 또는 sessionStorage를 통한 시스템 간 데이터 전달

### 4.5 재활용 인프라

| 컴포넌트 | 출처 | Author에서의 용도 |
|---------|------|-----------------|
| 텍스트 추출 (DOCX/PDF) | Compare/Translator | 소스 문서 파싱 |
| bge-m3 임베딩 | Explorer RAG | 항목 매칭 유사도 |
| Ollama 구조화 출력 | Compare AI 분류 | 요구사항 추출, 초안 생성 |
| Monaco 편집기 | editor-core.js | 초안 편집 |
| 파일 업로드 UI | Compare/Translator | 소스 문서 업로드 |
| 개인 작업공간 | Translator | `data/author/{user}/` |
| Markdown 렌더링 | Notebook 웹뷰 | 초안 미리보기 |

## 5. 분석 템플릿

### 5.1 기본 템플릿

시스템 내장 기본 템플릿 (범용):

| 카테고리 | 추출 항목 |
|---------|----------|
| 적용 범위 | 대상 장비, 적용 조건, 제외 사항 |
| 성능 요구 | 수치 기준, 허용 오차, 측정 방법 |
| 환경 조건 | 온도, 습도, 진동, 충격, 고도 |
| 시험 방법 | 시험 절차, 합격 기준, 시험 장비 |
| 재료/공정 | 재료 규격, 공정 조건, 품질 기준 |
| 참조 문서 | 인용 규격, 관련 표준 |

### 5.2 커스텀 템플릿 (향후)

사용자가 추출 항목을 직접 정의하여 템플릿으로 저장:
- 예: "EMI 시험 규격 템플릿" — 주파수 범위, 방사 레벨, 전도 레벨, ...
- JSON 형식으로 저장, 프로젝트 생성 시 선택

## 9. 설계 원칙

1. **사람이 판단, AI가 보조** — AI는 추출/분류/초안을 제안하고, 최종 결정은 항상 사람이 한다
2. **프로젝트 기반 영속성** — Author는 며칠에 걸친 작업이므로, Translator와 동일한 개인 작업공간 패턴
3. **Markdown이 공용 포맷** — 소스 추출, 초안 생성, 편집, 내보내기 모두 Markdown 기준
4. **기존 인프라 최대 재활용** — 새 라이브러리/모델 최소화, 플랫폼 내 검증된 컴포넌트 우선
5. **시스템 간 느슨한 연결** — Verify/Notebook 연계는 URL/API 기반, 하드 의존성 없음
