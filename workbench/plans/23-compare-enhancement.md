## 목표

Compare를 "두 문서 diff 도구"에서 **문서 품질 게이트 + 유사도 분석 플랫폼**으로 확장한다.
사용자 요청과 K-Spec 연계를 모두 반영하되, 각 Phase는 독립 배포 가능하게 설계한다.

## Phase 1: 유사도 검사 모드 (핵심 신규)

### 1.1 배경

현업 요구: 사내 스펙 문서가 외부 영문 원문(MIL-STD, AS, EN 등)을 참조해 작성되어 왔다. K-Spec 제정 시 원문과의 유사/동일 구간을 식별하여 표절 리스크를 사전 점검해야 한다.

카피킬러 같은 범용 표절 검사기와의 차별점:

| 카피킬러 | 이 기능 |
|---------|--------|
| 1:인터넷 전체 | 1:N (지정한 원문 문서들) |
| 한국어↔한국어 | **한국어↔영어** (크로스링구얼) |
| 정확한 문자열 매칭 위주 | 의미적 유사도 포함 (번역된 문장도 감지) |
| 외부 서비스 필수 | **폐쇄망 로컬 동작** |

### 1.2 동작 시나리오

```
1. 유사도 모드 선택 (툴바 3번째 탭)
2. 좌측: 검사 대상 문서 업로드 (작성 중인 K-Spec)
3. 우측: 참조 원문 1~N개 업로드 (영문 원본 스펙들)
4. [유사도 검사] 클릭
   ↓
   백엔드:
   a. 양쪽 문서 → 문장 분리 (kss/nltk)
   b. bge-m3로 문장 임베딩 (다국어, 크로스링구얼)
   c. 코사인 유사도 매트릭스 계산
   d. 임계값 기준 분류:
      - ≥0.90 → "동일 의심" (빨강)
      - ≥0.75 → "유사 의심" (주황)
      - <0.75 → 정상
   ↓
5. 결과 표시:
   - 좌측 패널: 유사 구간 하이라이트 (심각도별 색상)
   - 사이드바: 매칭 목록 (유사도 점수 + 원문 출처)
   - 클릭 시: 우측 패널에 원문 해당 구간 표시
6. 리포트 내보내기
```

### 1.3 백엔드 API

| 엔드포인트 | 메서드 | 설명 |
|-----------|--------|------|
| `/api/compare/similarity` | POST | 유사도 검사 실행 |

**입력**:
```json
{
  "target_paragraphs": ["검사 대상 문장들..."],
  "reference_docs": [
    { "filename": "MIL-STD-810G.pdf", "paragraphs": ["원문 문장들..."] }
  ],
  "threshold_identical": 0.90,
  "threshold_similar": 0.75
}
```

**출력**:
```json
{
  "summary": {
    "total_sentences": 120,
    "identical_count": 5,
    "similar_count": 12,
    "score": 85.8
  },
  "matches": [
    {
      "target_index": 3,
      "target_text": "차폐 효과는 40dB 이상이어야 한다",
      "reference_filename": "MIL-STD-461G.pdf",
      "reference_index": 42,
      "reference_text": "The shielding effectiveness shall be at least 40dB",
      "similarity": 0.94,
      "level": "identical"
    }
  ]
}
```

### 1.4 기술 구현

- **문장 분리**: 한국어 kss, 영어 nltk.sent_tokenize (또는 정규식 폴백)
- **임베딩**: bge-m3 (Explorer RAG 파이프라인에서 이미 사용 중)
  - 다국어 지원, 한↔영 크로스링구얼 유사도 가능
  - `backend/services/vector_index.py`의 모델 로딩 로직 재활용
- **유사도 계산**: numpy 코사인 유사도, 배치 처리
- **임계값**: `config.py`에 기본값, 관리자 설정에서 런타임 변경 가능

### 1.5 프론트엔드

- 기존 비교 모드/검증 모드와 동일한 탭 전환 패턴
- 우측 패널: 참조 원문 복수 업로드 UI (파일 목록 + 개별 삭제)
- 사이드바: 매칭 목록 (유사도 배지, 출처 파일명, 클릭 네비게이션)
- 하이라이트: `--diff-deleted-bg` (동일 의심), `--color-warning` (유사 의심) 계열
- 미니맵: 유사 구간 위치 마커

### 1.6 설계 결정

- **초기에는 세션 휘발성 유지** — 참조 원문도 매번 업로드. Compare의 무상태 원칙 유지.
- **참조 문서 라이브러리는 Phase 5에서 검토** — 사용 빈도 높으면 서버 저장 옵션 추가.
- **임베딩 캐시 없음 (초기)** — 문서 크기가 수백 문장 수준이면 실시간 계산 충분.

### 1.7 구현 순서

| # | 태스크 | 예상 |
|---|--------|------|
| 1a | 백엔드: 문장 분리 + bge-m3 임베딩 + 유사도 계산 API | 중 |
| 1b | 프론트엔드: 유사도 모드 탭 + 복수 원문 업로드 UI | 중 |
| 1c | 프론트엔드: 유사 구간 하이라이트 + 사이드바 매칭 목록 | 중 |
| 1d | 리포트 내보내기 (유사도 검사 결과) | 하 |
| 1e | 설정: 임계값 관리자 설정 + config.py 기본값 | 하 |

## Phase 2: 내보내기 확장

### 2.1 배경

현재 .txt만 지원. 실무에서는 Excel이나 HTML 형식의 공식 리포트가 필요.

### 2.2 구현 범위

| 형식 | 용도 | 구현 |
|------|------|------|
| Excel (.xlsx) | 공식 검토 기록, 관리자 보고 | openpyxl (백엔드 생성) |

- Sheet 1: 요약 (문서명, 날짜, 통계, 점수)
- Sheet 2: 변경점 목록 (번호, 유형, 판정, AI태그, 원문, 수정문)
- Sheet 3: 규칙 검증 결과 (이슈 목록, 심각도별)
- Sheet 4: 유사도 검사 결과 (Phase 1 완료 후)

## Phase 3: 규칙 검증 고도화

### 3.1 요구사항 문장 분류

기술문서의 요구사항 강도를 자동 분류:

| 분류 | 키워드 패턴 | 의미 |
|------|-----------|------|
| shall | ~하여야 한다, ~해야 한다 | 필수 요구사항 |
| should | ~하는 것이 바람직하다, ~권장한다 | 권고 |
| may | ~할 수 있다, ~허용한다 | 허용 |
| information | ~이다, ~있다 (서술) | 정보 서술 |
| test_condition | ~조건에서, ~환경에서 시험 | 시험 조건 |

→ Compare 검증 모드에 `requirement_classification` 규칙으로 추가

### 3.2 KAI 작성 지침 규칙

사내 문서 작성 지침이 확정되면 커스텀 규칙으로 추가:
- 규격 번호 표기법 (KAI-SPEC-XXXX)
- 표/그림 번호 체계
- 용어 통일 사전 확대

### 3.3 구현 순서

| # | 태스크 | 예상 |
|---|--------|------|
| 3a | 요구사항 문장 분류 규칙 (`requirement_classification`) | 중 |
| 3b | 분류 결과 사이드바 통계 (shall N건, should N건 ...) | 하 |
| 3c | KAI 지침 규칙 프레임워크 (지침 확정 후) | 보류 |

## Phase 4: 다중 문서 비교

### 4.1 배경

K-Spec Mother Spec 제정 시, 기존 유사 스펙 3~5개를 동시에 비교하여 공통점/차이점 매트릭스를 생성해야 한다. 이 결과가 문서 생성 시스템의 입력이 된다.

### 4.2 동작 시나리오

```
1. 다중 비교 모드 선택
2. 문서 2~5개 업로드
3. [비교 매트릭스 생성] 클릭
   ↓
   백엔드:
   - 모든 문서 쌍의 문장 유사도 계산
   - 공통 구간 / 문서별 고유 구간 / 충돌 구간 분류
   ↓
4. 결과:
   - 매트릭스 뷰: 문서 쌍별 유사도 히트맵
   - 목록 뷰: 공통/고유/충돌 구간 목록
   - 각 구간 클릭 시 해당 문서들의 원문 표시
```

### 4.3 문서 생성 시스템과의 연계

다중 비교 결과 → "공통 구간을 기반으로 통합 초안 생성" 프롬프트 → Ollama가 K-Spec 초안 생성

이 파이프라인은 별도 시스템이 아니라 다중 비교 모드의 확장 기능으로 구현:
- [초안 생성] 버튼 → 공통/고유/충돌 구간 + 프롬프트 → LLM
- 결과: Markdown 초안 → 다운로드 또는 편집기 연동

### 4.4 구현 순서

| # | 태스크 | 예상 |
|---|--------|------|
| 4a | 백엔드: 다중 문서 유사도 매트릭스 API | 상 |
| 4b | 프론트엔드: 매트릭스 뷰 + 목록 뷰 | 상 |
| 4c | LLM 초안 생성 파이프라인 (Ollama) | 중 |
| 4d | Markdown 초안 내보내기/편집기 연동 | 중 |

## Phase 5: 비교 세션 관리 (선택적)

### 5.1 배경

현재 Compare는 완전 무상태(휘발성). 사용 빈도가 높아지면:
- 비교 결과를 나중에 다시 보고 싶음
- 참조 원문을 매번 업로드하는 번거로움
- 리포트 이력 관리

### 5.2 구현 범위

- 비교 세션 저장/불러오기 (JSON export/import)
- 참조 문서 라이브러리 (자주 쓰는 원문 서버 저장)
- 리포트 이력 목록

### 5.3 판단 기준

사용자가 **"매번 같은 원문을 올리는 게 귀찮다"고 실제 피드백을 줄 때** 착수.
그 전까지는 YAGNI — 무상태 유지.
