## Phase 0: 모드 선택 허브 (진입점 재설계)

### 0.1 배경

현재 Verify 진입 시 **비교 모드**가 기본 화면으로 나타난다. 유사도 검사 모드가 추가되면 3개 모드(비교/검증/유사도)가 동급 기능인데, 항상 비교 모드가 선점하는 구조는 부적절하다.

업계 사례:
- **Beyond Compare** — 세션 타입 선택(폴더/텍스트/헥스) 후 전용 뷰 진입
- **Copyleaks** — 업로드 전 스캔 유형 선택 → 결과 화면
- **SonarQube** — 프로젝트 대시보드(품질 게이트 요약) → 이슈별 드릴다운

### 0.2 설계

Verify 진입 시 **모드 선택 허브**를 먼저 표시:

```
┌─────────────────────────────────────────┐
│  Document Verify                        │
├─────────────────────────────────────────┤
│                                         │
│   ┌──────┐  ┌──────┐  ┌──────┐         │
│   │ 비교 │  │ 검증 │  │유사도│         │
│   │      │  │      │  │ 검사 │         │
│   │ 두 문서│ │ 규칙 │  │ 표절 │         │
│   │ diff │  │ 점검 │  │ 점검 │         │
│   └──────┘  └──────┘  └──────┘         │
│                                         │
└─────────────────────────────────────────┘
```

- 각 카드 클릭 → 해당 모드의 전용 뷰로 전환
- 기존 **툴바 탭은 유지** — 모드 진입 후에도 탭으로 자유 전환 가능
- 허브는 "첫 진입점" 역할, 모드 간 전환은 기존 탭 패턴 그대로

### 0.3 장점

- 3개 모드가 **동등한 위상**으로 제시
- 카드에 모드 설명을 넣어 신규 사용자 안내
- 기존 비교/검증 뷰 코드 거의 그대로 유지
- 향후 모드 추가 시 카드만 추가

### 0.4 데이터 모델: 휘발성 유지 + 이탈 방지

업계 사례를 분석하면 검증 도구는 두 유형으로 나뉜다:

| 유형 | 대표 도구 | 저장 모델 |
|------|----------|----------|
| **도구형** | Beyond Compare, WinMerge, DiffNow | 휘발성 (세션) |
| **플랫폼형** | Turnitin, Copyleaks, SonarQube | 영속성 (계정별) |

현 시점에서 Verify는 **도구형**을 유지한다. 이유:
- 사용 패턴이 "파일 업로드 → 결과 확인 → 리포트 다운로드 → 종료"
- 영속화 시 저장소 구조, 목록 UI, 삭제 관리 등 부수 작업이 큼
- 반복 비교 요구가 확인되지 않았음 (Phase 4에서 피드백 기반 판단)

**단, 작업 중 이탈 방지는 필수:**

| 이탈 경로 | 대응 |
|----------|------|
| 브라우저 뒤로가기 / 새로고침 / 탭 닫기 | `beforeunload` 이벤트 |
| 시스템 스위처로 다른 시스템 이동 | 커스텀 확인 모달 |
| Home 버튼 (허브로 복귀) | 커스텀 확인 모달 ("새 작업을 시작하면 현재 작업이 초기화됩니다") |
| 모드 탭 전환 (비교→검증 등) | 파일 유지, 결과만 리셋 → 확인 불필요 |

## Phase 1: 유사도 검사 모드 (핵심 신규)

### 1.1 배경

현업 요구: 사내 스펙 문서가 외부 영문 원문(MIL-STD, AS, EN 등)을 참조해 작성되어 왔다. 자사 스펙 제정 시 원문과의 유사/동일 구간을 식별하여 표절 리스크를 사전 점검해야 한다.

**현업 피드백 반영 (2026-04-01)**:
- **1:1 비교 우선** — 당장은 대상 1개 vs 참조 1개. 1:N은 향후 확장
- **스캔 PDF 지원 필수** — 참조 원문 대부분이 과거 스캔 영문 PDF
- 텍스트 붙여넣기도 지원 (기존 비교/검증과 동일)

**현업 피드백 반영 (2026-04-02)**:
- **주 사용 시나리오는 영:영** — 영문 자사 스펙 vs 영문 원문(MIL-STD 등)
- 한↔영 크로스링구얼은 부차적 시나리오 (bge-m3가 동일 모델로 처리, 성능 차이 없음)
- 언어 옵션은 현 시점 불필요 (YAGNI) — 실제 한↔영 수요 발생 시 추가

카피킬러 같은 범용 표절 검사기와의 차별점:

| 카피킬러 | Verify 유사도 검사 |
|---------|-------------------|
| 1:인터넷 전체 | **1:1** (지정 원문, 향후 1:N 확장) |
| 한국어↔한국어 | **다국어** (영:영 주력, 한↔영도 지원) |
| 정확한 문자열 매칭 위주 | 의미적 유사도 포함 (패러프레이즈도 감지) |
| 텍스트 PDF 전용 | **스캔 PDF 지원** (OCR 자동 폴백) |
| 외부 서비스 필수 | **폐쇄망 로컬 동작** |

### 1.2 업계 표준 기법 분석

표절 검사 시스템은 다양한 기법을 조합하여 사용한다. 각 기법의 특성과 적용 가능성:

| 기법 | 원리 | 장점 | 단점 | 적용 |
|------|------|------|------|:----:|
| **Winnowing/Fingerprinting** | k-gram 해시 → sliding window 최솟값 선택 → 일치 탐지 | O(n), 위치 특정 가능, 삽입/삭제 강건 | 패러프레이즈 감지 불가, 크로스링구얼 불가 | ⚠️ |
| **N-gram Overlap (Jaccard)** | n-gram 집합 간 Jaccard/Containment 계수 | 극도로 단순/빠름 | 어순 변경/패러프레이즈 취약 | ⚠️ |
| **TF-IDF + Cosine** | TF-IDF 벡터 → 코사인 유사도 | 희귀 용어(규격 번호)에 강함, sparse 연산 빠름 | 의미 유사성 미반영, 단독 크로스링구얼 불가 | ✅ |
| **Semantic Embedding** | 사전학습 인코더(bge-m3)로 밀집 벡터화 → 코사인 유사도 | 패러프레이즈/크로스링구얼 감지 | GPU 유리, 임계값 튜닝 필요 | ✅ |
| **Seed-and-Extend** | fingerprint 일치 지점에서 양방향 확장 → 최장 유사 구간 | 정확한 구간 경계 특정 | seed 품질 의존, 구현 복잡 | ⚠️ |

### 1.3 상용 시스템 벤치마크

| 시스템 | 핵심 기법 | DB 의존 | 시사점 |
|--------|-----------|:-------:|--------|
| **Turnitin** | Fingerprint + seed-extend + 10B+ 문서 DB | 필수 | 대규모 DB 기반, 폐쇄망 불가 |
| **iThenticate** | Turnitin 엔진, 학술/출판 특화 | 필수 | CrossRef/PubMed 연동 |
| **Copyleaks** | Multi-layer: fingerprint → semantic AI → LLM 감지 | 클라우드 | 다국어 100+개, 하이브리드 파이프라인 참고 |
| **카피킬러** | N-gram + 한국어 형태소 분석 + KCI/RISS DB | 필수 | 한국 시장 1위, DB 의존적 |
| **MOSS** | Winnowing (k-gram fingerprint) | **로컬** | 소스 제출 기반 1:N — **우리 패턴과 동일** |

**결론**: 상용 시스템 대부분 인터넷 DB 의존. 폐쇄망에서는 MOSS 패턴(사용자 업로드 기반 로컬 비교)이 유일한 선택지. 단, 크로스링구얼은 semantic embedding으로 해결.

### 1.4 크로스링구얼 표절 검사 기법

> **참고**: 주 시나리오는 영:영이지만, bge-m3가 다국어를 동일 모델로 처리하므로 한↔영도 추가 비용 없이 지원된다.

다국어 간 유사도 검사에 사용 가능한 기법:

| 기법 | 원리 | 적용 |
|------|------|:----:|
| CL-ESA | 위키피디아 다국어 개념 벡터 매핑 | ❌ 위키 덤프 필요, 도메인 커버리지 낮음 |
| CL-ASA | 병렬 코퍼스로 언어 간 사전 구축 | ❌ 도메인 병렬 코퍼스 확보 어려움 |
| MT-based | 소스를 기계번역 → 동일 언어로 맞추고 비교 | ⚠️ Ollama 로컬 번역 가능하나 번역 품질이 병목 |
| **Multilingual Dense Embedding** | bge-m3/LaBSE/mE5로 언어 무관 벡터 공간 매핑 | ✅ bge-m3 한영 동시 지원, 이미 인프라 보유 |
| **하이브리드 (Embedding + 용어 매칭)** | 기술 용어/규격 번호는 exact match, 서술부는 embedding | ✅ 도메인 특성에 최적 |

**채택**: bge-m3 multilingual embedding을 주축으로, 규격 번호/약어는 정규식 exact match로 보완하는 **하이브리드 접근**. 주 시나리오(영:영)에서는 동일 언어 embedding 정확도가 더 높아 유리.

### 1.5 파이프라인 아키텍처

> 업계 표준은 2단계(Source Retrieval → Detailed Analysis)이나, **1:1 비교에서는 Stage 1이 불필요**하므로 정밀 비교만 수행한다. 향후 1:N 확장 시 Stage 1을 앞에 추가하면 된다.

```
[검사 대상 문서] ─── 텍스트 추출 ─── 문장 분리 ───┐
                                                     │
[참조 원문]      ─── 텍스트 추출 ─── 문장 분리 ───┤
       ↑                                             ▼
  스캔 PDF → OCR 자동 폴백            ┌─ 정밀 비교 (Detailed Analysis) ──┐
                                       │  ├─ 규격 번호/약어 exact match   │
                                       │  ├─ 문장 단위 bge-m3 유사도 행렬 │
                                       │  ├─ 최적 정렬 (DP 기반)          │
                                       │  └─ 임계값 분류 + 구간 병합      │
                                       └──────────────────────────────────┘
                                                     │
                                                     ▼
                                       결과: 구절별 유사도 점수 + 매핑된 문장 쌍
                                       → 사이드바이사이드 하이라이트 뷰
```

### 1.5-1 입력 처리 + 듀얼 포맷 아키텍처

3가지 입력 경로를 통합하고, 표시와 연산을 분리하는 듀얼 포맷을 적용한다.

**입력 경로**:

| 입력 유형 | 처리 |
|----------|------|
| 텍스트 PDF | PyMuPDF4LLM → MD 구조화 |
| 스캔 PDF | 자동 감지 → OCR → MD 구조화 |
| 텍스트 붙여넣기 | plain text → MD 래핑 |

**듀얼 포맷** (업계 표준 — Turnitin, Copyleaks 동일 패턴):

```
입력 → 텍스트 추출 (OCR 자동 폴백)
         ├─ (A) 구조화 MD → 웹뷰 렌더링 (사용자에게 보여주기)
         └─ (B) 정규화 plain text → 유사도 연산 (마크업 제거, 문장 분리)
```

- **(A) 표시용 MD**: 헤딩, 테이블, 볼드 등 문서 구조 유지. Notebook 웹뷰 렌더링 패턴 재사용
- **(B) 연산용 plain text**: MD 마크업 제거 후 순수 텍스트. 비교/유사도 품질 최적

> MD를 그대로 비교하면 `##`, `**`, `|` 등 마크업이 노이즈로 작용하므로, 표시와 연산을 반드시 분리한다.

### 1.5-2 스캔 PDF OCR 폴백

`rapidocr-onnxruntime`이 babeldoc 의존성으로 **이미 설치**되어 있음. 직접 호출하여 사용.

| 항목 | 결정 |
|------|------|
| OCR 엔진 | RapidOCR (onnxruntime) — 이미 설치됨, 추가 의존성 없음 |
| 대상 언어 | 영문 위주 (스캔 원문) |
| 감지 방식 | **자동 감지** (업계 표준) — 페이지당 텍스트 50자 미만 → 스캔 판정 |
| 테이블 처리 | img2table (OpenCV 라인 감지 → 셀 좌표) + 셀별 OCR |
| 이미지/다이어그램 | 텍스트 없는 영역은 자동 제외 |
| 적용 범위 | 유사도 모드 전용 (현 시점). 공통 함수로 구현하여 향후 비교/검증 확장 가능 |

**OCR 파이프라인**:
```
page.get_text() → 50자 미만?
  → Yes: page.get_pixmap(dpi=300) → RapidOCR
         테이블 영역 → img2table 셀 분할 → 셀별 OCR
  → No:  PyMuPDF4LLM으로 MD 구조화 (기존 경로)
```

> 관리자 설정에 OCR 관련 토글이 이미 존재 (`admin-settings.js:290`, `TRANSLATOR_OCR_WORKAROUND`). Verify 전용 설정은 `VERIFY_OCR_ENABLED` (기본 true)로 별도 추가.

### 1.6 임계값 설정

업계 embedding 유사도 기준 (bge-m3 기반):

| 수준 | 코사인 유사도 | 해석 | UI 표시 |
|------|:------------:|------|---------|
| 높은 유사 | **≥ 0.85** | 직역/복사 수준 | 빨강 (동일 의심) |
| 중간 유사 | **0.70 ~ 0.85** | 패러프레이즈 또는 동일 주제 | 주황 (유사 의심) |
| 낮은 유사 | **0.55 ~ 0.70** | 관련 내용, 참조 가능성 | 정보 제공 (선택적) |
| 무관 | **< 0.55** | 우연의 일치 수준 | 표시 안 함 |

**기술문서 주의사항**:
- 규격 문서는 도메인 용어 반복이 많아 baseline 유사도가 일반 텍스트보다 높음
- 따라서 임계값을 일반 텍스트 대비 **상향 조정** 필요
- **권장**: 파일럿 데이터 50~100쌍으로 ROC 곡선을 그린 후 최적 임계값 결정
- 초기 기본값은 `0.85 / 0.70`으로 시작, 사용자 피드백으로 튜닝

### 1.7 평가 지표

시스템 품질 측정을 위한 표준 지표 (PAN Competition 기준):

| 지표 | 정의 | 목표 |
|------|------|------|
| **Precision** | 검출된 유사 구간 중 실제 유사 비율 | 거짓 양성 최소화 |
| **Recall** | 실제 유사 구간 중 검출된 비율 | 누락 최소화 |
| **F1** | Precision과 Recall의 조화 평균 | 종합 성능 |
| **Granularity** | 하나의 유사 구간을 몇 개로 분할 감지했는지 (1 = 최적) | 과분할 페널티 |
| **Plagdet** | `F1 / log₂(1 + Granularity)` — PAN 공식 지표 | 구간 정확도 포함 종합 |

참고: PAN Competition 상위 시스템 plagdet 0.85~0.92, 크로스링구얼은 0.60~0.75.

### 1.8 동작 시나리오

```
1. 유사도 모드 선택 (허브 카드 또는 툴바 탭)
2. 좌측: 검사 대상 문서 업로드 (자사 스펙) — 파일 업로드 또는 텍스트 붙여넣기
3. 우측: 참조 원문 업로드 (원본 스펙) — 파일 업로드 또는 텍스트 붙여넣기
   ※ 스캔 PDF → 자동 OCR 추출 (사용자 개입 불필요)
4. [유사도 검사] 클릭
   ↓
   백엔드 (정밀 비교):
     a. 양쪽 문서 → 텍스트 추출 (스캔 시 OCR) → 문장 분리
     b. 규격 번호/약어 exact match (정규식)
     c. 문장 단위 bge-m3 유사도 행렬
     d. 최적 정렬 (Dynamic Programming)
     e. 임계값 기준 분류 → 인접 구간 병합
   ↓
5. 결과 표시:
   - 좌측 패널: 대상 문서 + 유사 구간 하이라이트 (심각도별 색상)
   - 우측 패널: 참조 원문 + 대응 구간 하이라이트
   - 사이드바: 매칭 목록 (유사도 점수 + 설명)
   - 클릭 시: 양쪽 패널 동기 스크롤 이동
6. 보조 도구 활용 (1.11-1 참조)
7. 리포트 내보내기 (Phase 2와 연동)
```

### 1.10 기술 구현

- **문장 분리**: 한국어 kss, 영어 nltk.sent_tokenize (또는 정규식 폴백)
- **규격 번호 매칭**: 정규식 패턴 (`MIL-STD-\d+`, `AS\d+`, `EN\s?\d+`, `KS\s?\w+` 등)
  - `js/config.js`에 이미 정의 예정 (backlog: 규격 번호 자동 링크)
- **임베딩**: bge-m3 (Explorer RAG 파이프라인에서 이미 사용 중)
  - 다국어 지원, 한↔영 크로스링구얼 유사도 가능
  - `backend/services/vector_index.py`의 모델 로딩 로직 재활용
- **유사도 계산**: numpy 코사인 유사도, 배치 처리
- **문장 정렬**: Dynamic Programming 기반 최적 정렬 (LCS 변형)
- **구간 병합**: 인접 유사 문장을 하나의 구간으로 병합 (gap tolerance 1~2문장)
- **임계값**: `config.py`에 기본값, 관리자 설정에서 런타임 변경 가능

### 1.12 수식 및 이미지 처리

| 요소 | 텍스트 PDF | 스캔 PDF | 처리 방식 |
|------|-----------|---------|----------|
| **수식** | PyMuPDF4LLM이 MathML/LaTeX로 추출 | OCR은 수식 인식 불가 → 이미지로 보존 | 텍스트 PDF: 기존 파이프라인. 스캔: 수식 영역을 이미지로 임베딩 |
| **일반 이미지** | PyMuPDF가 이미지 블록 감지 | 페이지 전체가 이미지 | 유사도 연산 대상 아님 (텍스트만 비교). MD 웹뷰에는 placeholder 또는 원본 이미지 표시 |

**원칙**: 유사도 비교는 **텍스트 대 텍스트**. 수식/이미지는 웹뷰 표시용으로만 보존하고, 연산에서는 제외. 스캔 PDF의 수식은 OCR 정확도가 낮으므로 무리하게 텍스트화하지 않는다.

### 1.13 설계 결정

- **듀얼 포맷** — 표시(MD 웹뷰)와 연산(plain text)을 분리. 업계 표준 패턴.
- **유사도 모드 우선** — OCR + 듀얼 포맷을 유사도에서 먼저 구현/검증. 비교/검증 확장은 검증 후.
- **공통 함수 설계** — OCR/추출 로직을 공통 함수로 구현하여 향후 비교/검증에서도 호출 가능하게.
- **세션 휘발성 유지** — 참조 원문도 매번 업로드. Verify의 무상태 원칙 유지.
- **임베딩 캐시 없음 (초기)** — 문서 크기가 수백 문장 수준이면 실시간 계산 충분.
- **하이브리드 접근** — embedding 단독이 아닌, 규격 번호 exact match와 결합. 기술문서 도메인에 최적.
- **파일럿 임계값 튜닝** — MVP 후 실제 문서 50~100쌍으로 ROC 곡선 그려 최적화.

## Phase 3: 규칙 검증 고도화 + 문서 인텔리전스 패널

### 3.0 배경

현재 검증 모드는 좌측 패널(문서 본문 + 이슈 하이라이트)만 사용하고 우측 패널을 숨긴다. 싱글 문서 뷰어로 인해 화면이 허전하고, 검증 결과가 사이드바 목록에만 표시되어 문서 전체 품질을 한눈에 파악하기 어렵다.

**해결**: 우측 패널을 **문서 인텔리전스 대시보드**로 활용한다.

```
┌──────────────────┬──────────────────┬────────────────┐
│  문서 본문        │  인텔리전스 패널  │  사이드바       │
│  (이슈 하이라이트) │  ┌─────────────┐ │  이슈 목록     │
│                   │  │평가표│구조│용어│ │  (네비게이션)  │
│                   │  ├─────────────┤ │               │
│                   │  │ 탭별 내용    │ │               │
│                   │  └─────────────┘ │               │
└──────────────────┴──────────────────┴────────────────┘
```

- 좌측: 문서 본문 + 이슈 하이라이트 (기존)
- 우측: 인텔리전스 패널 (신규) — 탭 전환 방식
- 사이드바: 이슈 네비게이션 (기존 역할 유지)

### 3.1 인텔리전스 패널 — 탭 1: 평가표 (Scorecard)

문서작성지침 항목별 준수 여부를 체크리스트 형태로 표시:

| 항목 | 내용 |
|------|------|
| 전체 등급 | A/B/C/D 등급 + 점수 (기존 스코어 링 확장) |
| 항목별 체크 | 지침 항목마다 ✅/⚠️/❌ + 건수 |
| 심각도 분포 | 오류/경고/제안 비율 차트 (바 또는 도넛) |
| 카테고리별 점수 | 구조 검사 / 용어 검사 / 가독성 검사 각각 점수 |

> 기존 사이드바 상단의 스코어 카드를 이 탭으로 이동하고 확장한다.

### 3.2 인텔리전스 패널 — 탭 2: 문서 구조 (Structure)

문서의 구조적 특성을 분석하여 표시:

| 항목 | 내용 |
|------|------|
| 장/절/항 트리 | 헤딩 기반 문서 구조 트리 (클릭 시 좌측 패널 이동) |
| 섹션별 분량 | 각 섹션의 단락/문장 수, 상대 비율 바 |
| 요구사항 분류 | shall/should/may/information/test_condition 통계 |
| 표/그림 번호 | 자동 감지된 표/그림 번호 목록 + 번호 체계 검증 |

**요구사항 문장 분류 기준**:

| 분류 | 키워드 패턴 (한국어) | 키워드 패턴 (영어) | 의미 |
|------|-------------------|-------------------|------|
| shall | ~하여야 한다, ~해야 한다 | shall, must, is required to | 필수 요구사항 |
| should | ~하는 것이 바람직하다, ~권장한다 | should, is recommended | 권고 |
| may | ~할 수 있다, ~허용한다 | may, is permitted | 허용 |
| information | ~이다, ~있다 (서술) | is, are, was (서술문) | 정보 서술 |
| test_condition | ~조건에서, ~환경에서 시험 | under the condition, test at | 시험 조건 |

> 주 시나리오가 영문 스펙이므로 영어 패턴을 우선 구현, 한국어는 후속 확장.

### 3.3 인텔리전스 패널 — 탭 3: 용어/참조 (Terminology)

문서 내 사용된 용어와 참조를 자동 추출하여 표시:

| 항목 | 내용 |
|------|------|
| 규격 번호 목록 | 자동 추출된 규격 참조 (MIL-STD-xxx, AS xxxx 등) + 출현 횟수 |
| 약어 목록 | 문서 내 약어 + 최초 정의 위치 (있으면) |
| 용어 일관성 | 동일 개념의 표기 불일치 감지 (예: "전자파 차폐" vs "EMI 차폐") |
| 단위 표기 | 사용된 단위 목록 + SI 단위 준수 여부 |

### 3.4 KAI 작성 지침 규칙

사내 문서 작성 지침이 확정되면 커스텀 규칙으로 추가:
- 규격 번호 표기법 (KAI-SPEC-XXXX)
- 표/그림 번호 체계
- 용어 통일 사전 확대

> 지침 규칙 결과는 평가표 탭에 자동 반영된다.

### 3.5 백엔드 API

| 엔드포인트 | 메서드 | 설명 |
|-----------|--------|------|
| `/api/verify/analyze-structure` | POST | 문서 구조 분석 (헤딩 트리, 섹션 분량, 표/그림 목록) |
| `/api/verify/classify-requirements` | POST | 요구사항 문장 분류 (shall/should/may 통계) |
| `/api/verify/extract-terms` | POST | 용어/규격번호/약어 자동 추출 |
| `/api/verify/scorecard` | POST | 전체 평가표 생성 (규칙 검증 결과 + 구조 분석 통합) |

> 검증 실행 시 기존 규칙 검사와 함께 구조/용어 분석을 병렬 실행하여 인텔리전스 패널을 채운다.

### 3.6 구현 순서

| # | 태스크 | 예상 | 의존 |
|---|--------|------|------|
| 3a | 인텔리전스 패널 UI 프레임 (우측 패널 + 3탭 구조) | 중 | — |
| 3b | 백엔드: 문서 구조 분석 API (`analyze-structure`) | 중 | — |
| 3c | 백엔드: 요구사항 문장 분류 (`classify-requirements`) | 중 | — |
| 3d | 프론트: 평가표 탭 (스코어카드 + 항목별 체크리스트) | 중 | 3a |
| 3e | 프론트: 구조 탭 (트리 + 분량 바 + 요구사항 통계) | 중 | 3a, 3b, 3c |
| 3f | 백엔드: 용어/규격번호/약어 추출 (`extract-terms`) | 중 | — |
| 3g | 프론트: 용어 탭 (규격 목록 + 약어 + 일관성) | 중 | 3a, 3f |
| 3h | 검증 실행 시 인텔리전스 데이터 병렬 로드 통합 | 하 | 3d~3g |
| 3i | KAI 지침 규칙 프레임워크 (지침 확정 후) | 보류 | — |

> **Phase 3 착수 시점**: Phase 1(유사도) 완료 후. Phase 2(내보내기)와 병행 가능.

## Phase 4: 세션 관리 + 이력

### 4.1 배경

현재 Verify는 완전 무상태(휘발성). 검증 결과는 브라우저 세션이 끝나면 사라진다.

**문제**:
- 허브 화면이 카드 3개만 있어 허전함
- "이 문서 검증했다"는 증거를 남길 수 없음
- "그때 결과 어땠지?" → 다시 올려서 돌려야 함
- 참조 원문을 매번 업로드하는 번거로움

**핵심 판단 (2026-04-02)**: 팀장/관리자 입장에서 검증 시스템의 가치는 **"검증 이력이 남고, 다시 열어볼 수 있는 것"**이다. 텍스트 이력만으로는 의미가 반감된다.

### 4.2 업계 영속화 모델 비교

| 모델 | 장점 | 단점 | 사례 |
|------|------|------|------|
| **계정별 자동 저장** | UX 최상, 이력 관리 | 저장소 관리 부담, 삭제 정책 필요 | Turnitin, Copyleaks |
| **프로젝트/세션 수동 저장** | 사용자 통제, 선택적 | UI 추가 필요 (저장/불러오기) | Beyond Compare (.bcss) |
| **리포트만 저장** | 최소 구현, 결과 재확인 | 원문 재비교 불가 | SonarQube |
| **JSON export/import** | 서버 저장소 불필요 | 파일 관리는 사용자 책임 | DiffNow |
| **카피킬러 모델** | 결과 저장 + 재열람 + 이력 | 서버 저장소 필요 | 카피킬러 |

**채택**: **카피킬러 모델 기반** — 검사 완료 시 자동 저장, 이력에서 재열람 가능. 3단계로 점진 구현.

### 4.3 구현 로드맵

#### Step 1: 이력 텍스트 표시 (허브 개선)

허브 허전함 해결 + Phase 4 디딤돌. 결과 **요약 정보만** 저장.

**저장 구조**: `data/verify/{username}/_history.json`
```json
[
  {
    "id": "20260402-153000-abc",
    "timestamp": "2026-04-02T15:30:00",
    "mode": "similarity",
    "files": { "a": "KAI-EMC-001.pdf", "b": "MIL-STD-461G.pdf" },
    "summary": "유사도 78.5% (높은 5건, 중간 12건)",
    "score": 78.5
  }
]
```

**허브 UI**:
```
        문서를 검증합니다
  ┌──────┐ ┌──────┐ ┌──────┐
  │유사도│ │ 비교 │ │ 검증 │
  └──────┘ └──────┘ └──────┘

  ──── 최근 작업 ─────────────────────────────────
  Similarity  KAI-EMC-001.pdf ↔ MIL-STD-461G.pdf   78.5%    2분 전
  Comparison  SWA_r1.docx ↔ SWA_r2.docx            +3 -1    어제
  Verification SWA_PMS_r1.docx                      85점     어제
```

- 최대 10건 표시 (FIFO, 오래된 것부터 삭제)
- 이력이 없으면 기존 힌트만 표시
- 클릭 시: 해당 모드로 전환만 (파일 자동 로드 없음 — Step 2에서 확장)

**백엔드 API**:

| 엔드포인트 | 메서드 | 설명 |
|-----------|--------|------|
| `/api/verify/history` | GET | 최근 이력 조회 (최대 10건) |
| `/api/verify/history` | POST | 이력 추가 (검사 완료 시 프론트에서 호출) |

**저장 시점**: 비교/검증/유사도 각 모드에서 **결과가 성공적으로 표시된 직후** 자동 호출.

#### Step 2: 결과 재열람 (세션 영속화)

검사 결과 전체를 저장하여, 이력에서 클릭 시 **결과를 다시 열어볼 수 있는** 구조.

**저장 구조**: `data/verify/{username}/{session_id}/`
```
session_id/
├── meta.json          # 모드, 파일명, 타임스탬프, 점수
├── file_a.txt         # 원문 텍스트 (paragraphs 또는 plain_text)
├── file_b.txt         # 비교문 텍스트 (비교/유사도 모드)
├── result.json        # 모드별 결과 데이터
│   - 비교: diffState (changes, decisions, aiClassifications)
│   - 검증: validateState (issues, score, summary)
│   - 유사도: similarity result (summary, matches)
└── file_a.md          # 유사도 모드: MD 렌더링용 (선택)
```

**허브 UI 확장**:
- 이력 항목 클릭 → 해당 모드로 전환 + 저장된 결과 자동 로드
- 결과 로드 시 문서 텍스트 + 분석 결과를 복원하여 하이라이트/사이드바 재현
- **읽기 전용** — 재열람 시 수정/재분석은 불가, 새로 올려야 함 (데이터 정합성)
- 이력 항목에 삭제 버튼 추가 (개인 작업공간 정리)

**백엔드 API 확장**:

| 엔드포인트 | 메서드 | 설명 |
|-----------|--------|------|
| `/api/verify/session` | POST | 세션 저장 (결과 + 원문 텍스트) |
| `/api/verify/session/{id}` | GET | 세션 로드 (재열람) |
| `/api/verify/session/{id}` | DELETE | 세션 삭제 |

**용량 관리**:
- 사용자당 최대 20세션 (초과 시 가장 오래된 것 자동 삭제)
- 원문 텍스트만 저장 (업로드 파일 원본은 저장하지 않음 — 용량 절약)
- 관리자 설정에서 최대 세션 수/보관 기간 설정 가능

#### Step 3: 참조 문서 라이브러리

자주 쓰는 참조 원문(MIL-STD 등)을 서버에 저장하여 매번 업로드 불필요.

**저장 구조**: `data/verify/{username}/library/`
```
library/
├── _index.json        # 라이브러리 문서 목록
├── {doc_id}/
│   ├── original.pdf   # 원본 파일
│   ├── extracted.txt   # 추출된 텍스트
│   └── extracted.md    # 유사도용 MD
```

**UI**:
- 유사도/비교 모드에서 파일 업로드 대신 "라이브러리에서 선택" 옵션
- 라이브러리 관리 UI (업로드/삭제/검색)
- 파일 업로드 시 "라이브러리에 저장" 체크박스

**백엔드 API**:

| 엔드포인트 | 메서드 | 설명 |
|-----------|--------|------|
| `/api/verify/library` | GET | 라이브러리 목록 |
| `/api/verify/library` | POST | 문서 추가 |
| `/api/verify/library/{id}` | DELETE | 문서 삭제 |
| `/api/verify/library/{id}/text` | GET | 추출된 텍스트 반환 |

### 4.4 구현 순서

| # | 태스크 | 예상 | Step |
|---|--------|------|:----:|
| 4a | 백엔드: 이력 저장/조회 API (`_history.json`) | 하 | 1 |
| 4b | 프론트: 허브 이력 섹션 UI (최근 10건 텍스트 표시) | 중 | 1 |

| 4d | 백엔드: 세션 저장/로드/삭제 API (개인 작업공간) | 중 | 2 |
| 4e | 프론트: 이력 클릭 → 결과 재열람 (읽기 전용 로드) | 상 | 2 |
| 4f | 세션 용량 관리 (자동 삭제, 관리자 설정) | 하 | 2 |
| 4g | 백엔드: 참조 문서 라이브러리 API | 중 | 3 |
| 4h | 프론트: 라이브러리 UI (선택/업로드/관리) | 중 | 3 |
