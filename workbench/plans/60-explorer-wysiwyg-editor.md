## 0. 한 줄 요약

현재 Explorer 편집기(Monaco · **원본 HTML 직접 편집**)는 비전문가에게 진입장벽이 높다.
→ **일반 엔지니어용 "신규 문서 작성 경로"를 Toast UI Editor(마크다운↔WYSIWYG 토글, 무빌드 드롭인)로 추가**한다.
기존 변환 웹북(복잡 HTML)은 Monaco 유지로 안전 보존. 동시 편집은 **배타적 잠금+담당자+위임**으로 데이터 손실을 막는다.

## 1. 배경 · 현재 구조

### 현재 Explorer 편집 흐름 (조사 결과)
- 편집기: **Monaco** (`js/editor-core.js` `EditorCore.create`, `js/editor.js` Explorer 어댑터)
- 콘텐츠: **원본 HTML** (DOCX→HTML 변환 웹북). 분할 뷰(소스 | 미리보기), Ctrl+S 저장
- 저장: `POST /api/save-document` `{path, content, createBackup}` → `.html` 파일 직접 갱신
- 로드: `GET currentPage?t=...` → `EditorCore.open(content, docPath)`
- **자가 호스팅 검증됨**: Monaco 가 `js/monaco-editor/vs/` 트리로 폐쇄망에서 이미 동작 → "에디터 번들 통째로 self-host" 패턴은 우리 환경에서 이미 성공 사례 보유
- 어댑터 패턴(Strategy): `language('html'|'markdown')`, `renderPreview`, `onSave`, `onClose`, `resolveAssets`
  - 현재 2개 어댑터: **Explorer(HTML)** · **Translator/Notebook(Markdown, marked+DOMPurify 미리보기)**
- RBAC: `editor`/`admin` 만 편집 버튼 노출(`.auth-editor-only`), 서버측 API 권한 + 클라 CSS 은닉

### 문제 의식
- "문서 편집기가 너무 전문가용" → HTML 소스를 직접 만지는 UX 는 일반 엔지니어에게 부담
- 목표: **일반 엔지니어가 쉽게 작성·공유**하는 협업 문서 공간으로 성숙도 확장

## 2. 핵심 갈림길 — 콘텐츠 모델 (의사결정 #1)

> 이 한 가지가 후보 선택·통합 난이도·리스크 전부를 좌우한다. 다른 모든 논의의 전제.

현재 Explorer 콘텐츠는 **변환 파이프라인이 생성한 복잡 HTML** 이다:
- 표: `rowspan`/`colspan` 병합 (python-docx raw XML 순회로 정밀 변환)
- 수식: **MathML** (OMML→MathML, 브라우저 네이티브 렌더)
- provenance 주석(`<!-- converter: ... -->`), 장절번호·캡션 합성 구조
- 검색 인덱스·RAG 파이프라인이 이 HTML 구조에 의존

**어떤 WYSIWYG 도 이 HTML 을 무손실 왕복(round-trip)하지 못한다.**
- 마크다운 기반(Toast UI): 저장 시 마크다운으로 직렬화 → **병합 표·MathML 소실**
- 자체 스키마형(TinyMCE/CKEditor): 미지의 노드(MathML, custom attr) **정규화 과정에서 제거·왜곡**

→ 그러므로 선택은 둘 중 하나다:

| 방향 | 정의 | 콘텐츠 | 위험 |
|------|------|--------|------|
| **A. 신규 작성 경로** | 일반 엔지니어가 **새 문서**를 마크다운/WYSIWYG 로 작성 | **마크다운(.md)** 신규 저장 | 콘텐츠 포맷 이원화(HTML+MD) → 서빙·검색·RAG 변환 비용 |
| **B. 기존 HTML 비주얼 편집** | 같은 HTML 을 Monaco(소스)↔WYSIWYG(시각) 토글 | **HTML 단일** 유지 | 복잡 문서 무손실 왕복 불가 → "안전 문서"로 제한 필요 + 라이선스 마찰 |

**제안: 방향 A 를 1차 목표로.** 사용자의 진짜 의도("일반 엔지니어가 새 문서를 쉽게 작성")는
기존 학술 변환 웹북을 비주얼로 고치는 게 아니라 **신규 저작 진입장벽을 낮추는 것**이다.
기존 변환 웹북은 Monaco(파워유저) 유지가 안전하다. (상세 §6)

## 3. 업계 표준 · 일반적 방식 (조사)

### "두 모드 함께 지원"은 보편적이다
질문하신 "보통 두 모드를 함께 지원하는가?" → **그렇다, 사실상 표준.**
- GitHub/GitLab 이슈·위키: 마크다운 ↔ Preview/Rich 토글
- Discourse, StackOverflow: 마크다운 + 시각 보조
- Notion·계열: 블록 WYSIWYG (단, 마크다운 단축 입력 흡수)
- **Toast UI Editor 의 정체성 자체가 "Markdown ↔ WYSIWYG 탭 토글"** — 헤드라인 기능

핵심 패턴: **단일 콘텐츠(주로 마크다운)를 두 가지 뷰로 편집**. 우리 EditorCore 의
`language` + `renderPreview` 분할 뷰 철학과 동일 계열.

### "네이버 본사 편집기" 실사 — SmartEditor2 (별도 확인)
- `naver/smarteditor2` = 네이버 corp. 가 직접 공개한 진짜 네이버표 WYSIWYG (NHN/Toast UI 와 구분됨)
- LGPL 2.1 · WYSIWYG+HTML+TEXT 3모드 · **HTML 출력** · 자가호스팅 가능
- **탈락 사유**: ① **Jindo 프레임워크 의존**(무프레임워크 규칙 위반) ② iframe 기반 레거시(2014~2019) ③ 코어 v2.10.0 이후 **사실상 유지보수 중단** ④ 최신판 SE3/SmartEditor ONE 은 **비오픈소스**(폐쇄망 불가)
- 결론: "네이버 제작" 키워드엔 부합하나 무프레임워크·유지보수·모던 UI 전 항목에서 Toast UI 에 열세 → **비권장**(방향 B HTML 단일 고집 시에만 한정 후보)

### 2026 트렌드 재검증 — 제약이 결정한다 (의사결정 #2)
- **요즘 대세**: 블록형(Notion) + ProseMirror/Lexical 헤드리스 + Yjs 협업 → **TipTap·Milkdown/Crepe·BlockNote·Lexical**
- 품질·미래성은 이들이 Toast UI 보다 앞섬. **그러나 전부 우리 제약에 탈락**:
  - TipTap: standalone UMD 번들 없음, ES모듈+esm.sh 방식 → 폐쇄망엔 번들러 필요. Milkdown/Crepe·Lexical 동일. BlockNote=React(무프레임워크 위반)
- **드롭인 번들(=Monaco처럼 벤더링)을 그냥 주는 모던 옵션 = Toast UI(마크다운+WYSIWYG), Editor.js(블록 JSON) 둘뿐**
- **Editor.js 격상**: 블록 UX 가 일반 사용자에 더 친숙(트렌드 부합)하나, **출력이 블록 JSON** → 서빙·검색·RAG 통합 마찰 최대, 표·수식 약함, 블록별 플러그인 다발 벤더링
- **숨은 핵심 레버 — "무빌드" 제약 재고**:
  - Monaco(`js/monaco-editor/vs/`)는 이미 **사전 빌드 산출물을 정적 벤더링**한 것. 규칙의 실질 = "런타임/배포에 번들러 금지"이지 "수작업 JS 강제"가 아님
  - 오프라인서 1회 번들 빌드 → 정적 커밋 → 폐쇄망 서빙 = 런타임 에어갭 안전(Monaco 선례)
  - 이 완화를 허용하면 **TipTap·Milkdown/Crepe 후보 개방**. 차이: Toast UI/Editor.js 는 기성 번들 수령(업그레이드 마찰 0), TipTap/Milkdown 은 우리가 1회 조립+유지
- **결론 매트릭스**:
  | 제약 | 권고 |
  |------|------|
  | 무빌드 고수(드롭인만) | **Toast UI**(1순위) vs **Editor.js**(블록 트렌드) 택1 |
  | "1회 빌드 후 벤더링" 허용 | **TipTap** 또는 **Milkdown/Crepe**(트렌드·확장성·미래성 우위) |

### Toast UI Editor 유지보수 실사 (리스크 점검)

## 4. 다각도 평가 (코드 · UI/UX · 웹디자인 · 사용자)

### 🧑‍💻 코드 전문가
- **EditorCore 어댑터는 Monaco 전제** — Toast UI 는 Monaco 언어 교체가 아니라 **별도 풀 에디터**.
  → "EditorCore 어댑터 추가"가 아니라 **EditorCore 와 동급의 2번째 편집기 엔진**을 모달 안에 끼우는 작업.
  분할 뷰·모달·저장 훅 인프라는 재사용하되, 엔진 추상화 1단계 더 필요.
- 무빌드 제약이 TipTap 을 즉시 탈락시킴 → 후보가 Toast UI / Quill / (HTML이면)TinyMCE 로 좁혀짐.
- 콘텐츠 이원화(HTML+MD)는 **검색 인덱스·RAG·서빙 전 경로**에 영향 → MD→HTML 렌더 일관성이 숨은 핵심 작업.
- **가역성**: 기존 Monaco 경로 100% 유지 + 신규 경로 추가 → 롤백 안전. ✅

### 🎨 UI/UX 전문가
- "모드 스위치" 자체가 정답 패턴 — **신규 사용자는 WYSIWYG, 파워유저는 소스**, 같은 문서를 두 시야로.
- Toast UI 의 탭 토글 = 학습 비용 거의 0. 마크다운 단축키도 흡수해 "키보드 파워유저"도 만족.
- 주의: **모드 전환 시 데이터 손실 경고** UX 필수(복잡 HTML→MD 변환 불가 문서는 토글 비활성).
- 우리 디자인 토큰(`--active-color` 블루 통일)과 Toast UI 기본 테마의 **시각 충돌** → CSS 토큰 오버라이드 레이어 필요.

### 🖌️ 웹디자인 전문가
- Toast UI 기본 스킨은 모던하나 **우리 플랫폼 헤더·모달 시스템과 톤 통일** 작업 필요(`tokens.css` 변수 매핑).
- 다크모드: Toast UI 다크 테마 존재 → 우리 다크 토큰과 브리지. 하드코딩 색 금지 규칙 준수해야.
- 모달 안 임베드(`.modal-box`) vs 전용 작성 화면 — 신규 저작은 **전용 풀스크린**이 쾌적.

### 👤 사용자(일반 엔지니어)
- "HTML 안 만지고 글 쓰고 표·이미지·코드블록 넣고 공유" = 정확히 충족.
- 마크다운은 엔지니어 친화적(Git/README 문화) + WYSIWYG 는 비개발 직군 포용 → **두 직군 동시 만족**.
- 공유: 작성→웹북 뷰로 즉시 공개되는 흐름이 자연스러움.

## 5. 권고안

### ⭐ 전문가 결론 (업계표준·경험자 관점, 결정형)
> **마크다운을 원본으로 하는 "신규 문서 작성 경로"를 Toast UI 로 추가. 기존 변환 웹북은 Monaco 유지. 무빌드 규칙은 v1 에서 고수.**
- **근거 1**: 엔지니어 문서 도구의 표준 = 마크다운 원본 + WYSIWYG 레이어(GitHub/GitLab/Confluence/Notion/Docusaurus/MkDocs 수렴). 이식성·diff·검색·기존 marked 파이프라인 정합.
- **근거 2**: 들여온/변환 문서와 신규 저작 문서를 **분리**(업계 관행). 복잡 HTML 무손실 편집을 한 에디터에 강요하지 않음.
- **근거 3**: Toast UI = "지루하지만 옳은" 선택. 드롭인 번들로 추가 도구 0(Monaco 선례), MIT·폐쇄망, 1인 유지보수에 맞는 보수적 안.
- **근거 4 (YAGNI)**: 트렌드(TipTap/노션형)는 알지만 v1 에서 빌드 파이프라인 부담 선제 수용은 손해. 가치 먼저, 투자 나중.
- **근거 5**: Editor.js(블록형)는 출력이 전용 JSON → 콘텐츠 락인. 마크다운 이식성 포기 이유 없음 → **탈락**.
- **마음 바꿀 단 하나**: "실시간 협업·노션형 블록 편집"이 플랫폼 핵심 제품 베팅이면 → 무빌드 규칙 의식적 완화 + **TipTap+1회 번들 빌드**로 전환.



### 1차 권고: **Toast UI Editor 기반 "신규 문서 작성" 경로 (방향 A)**
- 일반 엔지니어가 **마크다운↔WYSIWYG 토글**로 새 문서 작성, **`.md` 로 저장**
- 서빙·검색·RAG 용 **HTML 렌더는 기존 마크다운 파이프라인(Plan-17/marked+DOMPurify) 재사용**
- 기존 변환 웹북(복잡 HTML)은 **Monaco 유지** — 무손실·안전
- 근거: 무빌드·MIT·폐쇄망·한국어·두 모드 내장 = 우리 제약 전부 충족, 질문하신 "네이버 제품"이 바로 이것

### 대안(방향 B): 같은 HTML 을 Monaco↔WYSIWYG 토글
- 단일 HTML 유지가 최우선이고 콘텐츠 이원화를 피하고 싶다면
- TinyMCE(GPL·브랜딩) 또는 CKEditor5(GPL/키) 로 **"WYSIWYG 안전 문서"에 한정** 토글
- 단, 복잡 변환 웹북은 토글 차단 → 사실상 "신규/단순 문서만 시각편집" = 방향 A 와 도달점 유사하나 통합·라이선스 마찰 더 큼
- **권고: 방향 A 우선, B 는 추후 옵션**

## 6. 통합 설계 스케치 (방향 A 채택 시)

```
[새 문서 작성] 버튼(.auth-editor-only)
  → 전용 작성 화면 (또는 모달)
  → Toast UI Editor 인스턴스 (js/lib/tui-editor/ 자가호스팅 번들)
      ├ Markdown 탭 ↔ WYSIWYG 탭 토글
      └ 저장: 마크다운 텍스트
  → POST /api/save-document (또는 신규 /api/documents) { path:*.md, content, ... }
  → 서빙 시 marked+DOMPurify 로 HTML 렌더 (기존 파이프라인)
  → 검색/RAG: html_to_text → 인덱스 (기존 경로 재사용)

[기존 웹북 편집] = 변경 없음 (Monaco/HTML)
```

- 추상화: EditorCore 위에 `EditorEngine` 선택 레이어(Monaco | ToastUI) 1단계 추가, 모달/저장 훅 공유
- 번들 고정: `js/lib/tui-editor/` 에 특정 버전 동결(Monaco 선례)
- 디자인: `tokens.css` 변수→Toast UI CSS 변수 매핑 시트 1개

## 6-A. 동시 편집·충돌 대비 (업계 관행) — **신규 보강**

### 현재 상태 (사실 확인 · 2026-06-15)
- `backend/api/document.py` `save_document` = **권한체크 → 백업 → 파일 덮어쓰기**가 전부.
- **버전/ETag/잠금/ mtime 검사 전무 = last-write-wins.** 두 편집자가 같은 문서 저장 시 **뒤 저장이 앞 저장을 조용히 덮음.** 복구는 `backups/` 타임스탬프 백업뿐.
- 현재는 "주로 1인 편집" 전제라 표면화 안 됐을 뿐 → **공유 문서 공간 전환 시 실데이터 손실 리스크.**

### 업계 관행 (가벼움 → 무거움)
1. **낙관적 잠금(ETag/If-Match → 412/409)** — 웹 표준. GET 시 버전 토큰 반환 → 저장 시 동봉 → 서버가 stale write 거부. (강제 잠금은 웹에서 비현실적: 방치 락)
2. **편집 중 표시(soft lock/presence)** — heartbeat 기반 "○○님 편집 중" 배너. 경고용(강제X).
3. **자동저장 + 버전 이력** — 주기 draft 저장 + 스냅샷/복원. 충돌 전략과 무관하게 손실 감소.
4. **실시간 협업(CRDT/Yjs)** — 동기화 서버·웹소켓 필요 → **폐쇄망 v1 제외(과설계).**

### 채택 결정 (2026-06-15 사용자 결정) — 배타적 잠금 + 담당자 소유권 + 위임
- 실시간 협업 **불필요**. **"편집 중이면 타인 편집 불가 / 담당자만 편집"** 채택 (= 배타적 잠금·문서 체크아웃, 업계 일반 방식).
- 구성:
  - **담당자(소유자)**: 문서별 편집 담당 1인 → 담당자만 편집 버튼 노출
  - **편집 잠금**: 담당자가 편집 시작 시 잠금 → 종료 시 해제
  - **위임(handover)**: 담당자 변경 버튼 → 다른 사용자에게 이양
- **필수 안전장치 (방치 잠금 대비)**: ① 무활동 N분 **자동 해제** ② 관리자 **강제 잠금 해제·담당자 재지정**
- 보조(선택): 자동저장/버전이력은 병용 가능. 실시간 협업(CRDT)·낙관적 머지는 **제외**.
- **소급 적용**: 동시수정 갭은 **기존 Explorer(Monaco/HTML)에도 현존** → 잠금·소유권을 신규/기존 양쪽 공통 적용 가치.

## 6-B. 마이그레이션·롤아웃 방법론 + 전/후 비교·체크리스트 — **신규 보강**

### 업계 관행 (Payload·GitLab·MS 공통)
- **빅뱅 교체 금지** → 구(Monaco)·신(Toast UI) **병행 + 토글**, 단계 롤아웃: **opt-in → 기본 → 구버전 폐기**
- **기능 패리티 매트릭스** + **콘텐츠 왕복(round-trip) 검증** + **온더플라이 변환 훅**(MD↔HTML)

### 전/후 비교용 사전조사 (베이스라인 캡처)
- **현행 인벤토리**: 현 에디터 기능 목록 · 사용자(편집자/관리자) · 기존 콘텐츠 유형

- **대표문서 코퍼스**: 단순/표/수식/이미지 포함 샘플 N개 고정 → 왕복 무결성 회귀셋
- **작성 소요시간 베이스라인**: "지금 새 문서 1건 작성·서식까지 X분" 측정 → 개선 정량화

### 체크리스트 3종 (계획서 부속)
- **기능 패리티** (필수 / 선택 / 제외): 표·코드블록·이미지·링크·헤딩·목록 · (수식은 제외 또는 후순위)
- **수용·QA**: 콘텐츠 왕복 무결성 · RBAC(editor/admin) · 다크모드 · 디자인 토큰 정합 · 접근성 · 브라우저 · **자동저장·충돌처리** · **검색/RAG 흡수**(신규 MD → html_to_text → 인덱스)
- **롤백**: Monaco 경로 100% 유지 · 신규 토글 off 즉시 복귀

### 성공 지표

## 7. 리스크 · 미해결 의사결정

### 리스크
| 항목 | 영향 | 완화 |
|------|------|------|
| 콘텐츠 포맷 이원화(HTML/MD) | 검색·RAG·서빙 일관성 | MD→HTML 단일 렌더 경로 고정, 신규는 MD 전용 |
| 복잡 HTML 무손실 왕복 불가 | 사용자 혼란 | 변환 웹북은 WYSIWYG 차단, 명시적 경고 UX |
| Toast UI 저빈도 유지보수 | 장기 보안·버그 | 버전 동결+자가호스팅, 이슈 모니터 |
| 디자인 톤 불일치 | 브랜드 이질감 | 토큰 매핑 레이어, 다크모드 브리지 |
| 무빌드 제약 | TipTap 등 배제 | 후보를 UMD 드롭인으로 한정(이미 반영) |
| **동시 수정(현재 방어 없음)** | 공유 시 데이터 손실 | 배타 잠금+담당자+위임+자동/강제 해제(§6-A), 기존 경로 소급 |
| **방치된 잠금** | 편집하다 떠나면 영구 잠김 | 무활동 자동 해제 + 관리자 강제 해제 (필수) |
