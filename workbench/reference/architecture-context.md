- **자체 호스팅 필수**: 모든 구성요소가 사내 서버에서 운영 가능해야 함

- **기존 인프라 활용**: 사내 LDAP/AD 인증 체계, 기존 문서 관리 체계와 연동 필요

## 2. 비교 서브시스템 (현재 개발중)

### 2.1 현재 모듈 구성

비교 서브시스템은 3개 모듈로 구성되어 개발 중:

| 모듈 | 기능 | 현재 상태 |
|------|------|----------|
| 텍스트 비교 | 두 문서 간 텍스트 수준 diff | 개발중 |
| 의미 비교 | 두 문서 간 의미적 동등성/차이 분석 | 개발중 |
| 규칙 준수 검사 | 문서가 정해진 작성 규칙을 따르는지 검증 | 개발중 |

### 2.2 비교 서브시스템과 NLP 기능의 관계

인제대 최용선 교수팀의 NLP 시스템(아래 섹션 5 참조)의 기능들이 비교 서브시스템의 3개 모듈과 직접 대응됨:

- **텍스트 비교** ↔ 문서 변경 처리, 대체 문구 제시
- **의미 비교** ↔ 의미 유형별 용어 추출, 문장 의미 컴포넌트 파싱, 시맨틱 XML
- **규칙 준수 검사** ↔ PPA 18 Human Error Trap 검증, 작성 지침 준수 검증

### 2.3 Claude Code에게 요청할 분석 포인트

- [ ] 현재 비교 서브시스템의 코드 구조에서, 문서 분석 로직이 비교 로직과 어느 정도 결합되어 있는지 확인
- [ ] 문서 파싱, 전처리, 용어 추출 등의 로직이 비교 모듈 내부에 하드코딩되어 있다면, 이를 분리 가능한 구조인지 평가
- [ ] 현재 API 설계(있다면)가 외부 시스템(K-Spec 등)에서 호출 가능한 구조인지 확인

## 3. K-Spec 관리 시스템 (신규 기획)

### 3.1 K-Spec 개념

K-Spec은 KAI의 표준 기술문서(규격서/스펙) 체계를 수립하는 과제:

- **Mother Spec (모체 스펙)**: 기존 분산된 스펙들을 분석하여 통합한 표준 스펙
- **Branch Spec (파생 스펙)**: Mother Spec에서 사업별/용도별로 파생된 스펙
- **Specification Tree**: 전체 스펙의 계층적 관계 (L0→L1→L2→L3)

### 3.2 Spec Tree 계층 모델

| Level | 명칭 | 설명 | 예시 |
|-------|------|------|------|
| L0 | K-Spec Master (Mother Spec) | 회사 전체 표준 스펙의 근간 | KAI-SPEC-0001 항공전자장비 일반 요구사항 |
| L1 | Domain Spec (분야별) | L0에서 파생된 분야별 표준 | KAI-SPEC-0001-E 항공 전자장비 EMI 요구사항 |
| L2 | Program Spec (사업별) | L1에서 파생된 사업 특화 스펙 | KAI-SPEC-0001-E-KF21 KF-21 항전 EMI 요구사항 |
| L3 | Component Spec (구성품) | L2에서 파생된 구성품/부품 수준 | KAI-SPEC-0001-E-KF21-RAD 레이더 모듈 EMI |

### 3.3 제안된 기술 스택

| 영역 | 기술 | 에어갭 호환성 |
|------|------|------------|
| Frontend | React 18+ / TypeScript / Tailwind CSS / Monaco Editor | ✓ 빌드 후 정적 파일 배포 |
| Backend API | Python 3.11+ / FastAPI / SQLAlchemy / Celery | ✓ pip 오프라인 미러링 |
| Git 저장소 | Gitea (Self-hosted) | ✓ 에어갭 완전 호환 |
| DB | PostgreSQL 15+ | ✓ 오픈소스 |
| 검색엔진 | Elasticsearch 8+ (또는 OpenSearch) + nori | ✓ 자체 호스팅 |
| 파일저장 | MinIO (S3-compatible) | ✓ Go 단일 바이너리 |
| 컨테이너 | Docker + Docker Compose (또는 Podman) | ✓ 이미지 사전 빌드 후 전송 |
| 메시지 브로커 | Redis | ✓ 자체 호스팅 |

### 3.4 핵심 기능 모듈

1. **스펙 문서 작성/편집**: Markdown + YAML Frontmatter 기반, 웹 에디터(WYSIWYG)
2. **버전/브랜치 관리**: Git 기반, Mother→Branch 파생, cherry-pick/merge로 변경 전파
3. **문서 비교/분석**: 기존 비교 서브시스템과 통합 (→ 문서 분석 서비스 API 호출)
4. **Spec Tree 시각화**: D3.js 기반 인터랙티브 트리, 연관 스펙 Quick View
5. **승인/배포 워크플로우**: 초안→팀리뷰→부서승인→CCB승인→배포(Baseline)

### 3.5 K-Spec UI/UX 주요 화면

| 화면 | 핵심 구성요소 | 대상 사용자 |
|------|-------------|----------|
| 대시보드 | 요약카드(전체스펙수, 진행률, 리뷰대기, 참여팀), 상태별/팀별 현황 차트, 스펙 작성현황 테이블 | 표준화 관리자 |
| Spec Tree | 계층형 트리뷰(L0~L3), 레벨별 색상코드, 연관스펙 Quick View 패널 | 모든 사용자 |
| 스펙 상세 | 좌: 문서편집기+탭(내용/이력/비교/리뷰), 우: 메타데이터+연관스펙+파생경로 | 스펙 작성자 |
| 문서 비교 | side-by-side diff, 중복/차이/불일치 하이라이트 | 작성자/리뷰어 |
| 통합 검색 | Ctrl+K 단축키, 스펙ID/스펙명/본문 통합검색, 필터(레벨/상태/팀/사업) | 모든 사용자 |

### 3.6 ADR (Architecture Decision Records)

| ADR | 결정 | 근거 |
|-----|------|------|
| ADR-001 | 스펙 저장 형식: Markdown + YAML Frontmatter | Git diff 호환, 변경 추적 용이, 메타데이터 구조화 |
| ADR-002 | 버전관리: Git 브랜치 = Spec Tree 계층 매핑 | Mother=main, Branch=git branch, Baseline=tag |
| ADR-003 | 검색: Elasticsearch + nori 한국어 형태소 분석 | 한/영 혼용 문서, 전문 용어 검색 지원 |
| ADR-004 | 기존 비교 서브시스템 통합 | 텍스트/의미/규칙 3개 모듈을 분석 파이프라인에 통합 |

## 4. 문서 분석 서비스 — 핵심 제안

### 4.1 제안 배경

NLP 기반 문서 분석 기능(파싱, 용어 추출, 유사도 분석, 규칙 검증 등)은 비교 서브시스템과 K-Spec 모두에서 필요함. 어느 한쪽에 넣으면 다른 쪽에서 중복 구현하거나 의존성이 꼬이게 됨.

### 4.3 문서 분석 서비스 API 목록 (우선순위별)

#### 1순위 — 즉시 구현 가능, 난이도 낮음

| API | 입력 | 출력 | 구현 방법 | 활용처 |
|-----|------|------|---------|--------|
| `POST /parse/structure` | Word/PDF 파일 | 장/절/항 계층 JSON | python-docx, pdfplumber | 비교, K-Spec |
| `POST /extract/metadata` | Word/PDF 파일 | 문서명, 규격번호, 버전, 적용범위 등 | 정규표현식 + 위치 규칙 | K-Spec Spec Tree 자동 구성 |
| `POST /extract/references` | 문서 텍스트 | 참조 문서 ID 목록 + 관계 유형 | 정규표현식 패턴 매칭 | 비교, K-Spec 연관스펙 |
| `POST /analyze/statistics` | 문서 텍스트 | 페이지수, 요구사항수, 표/그림수 등 | 카운팅 + 패턴 매칭 | K-Spec 대시보드 |

#### 2순위 — K-Spec 제정에 직접 도움, 중간 난이도

| API | 입력 | 출력 | 구현 방법 | 활용처 |
|-----|------|------|---------|--------|
| `POST /extract/terms` | 문서 텍스트 | 도메인 용어 목록 (장비명, 재료명, 규격번호 등) | KoNLPy(Mecab) + TF-IDF + 사용자사전 | 비교(의미비교), K-Spec, 번역 |
| `POST /classify/requirements` | 문장 목록 | 유형 분류 (shall/should/may/정보서술/시험조건) | 키워드 패턴 + 종결어미 패턴 | 비교(규칙검사), K-Spec |
| `POST /analyze/similarity` | 문장 쌍 또는 문서 쌍 | 유사도 점수 + 유사 문장 매핑 | Sentence-BERT (로컬 모델) + 코사인 유사도 | 비교(의미비교), K-Spec 중복탐지 |

#### 3순위 — 가치 높지만 난이도 높음, 단계적 접근

| API | 입력 | 출력 | 구현 방법 | 활용처 |
|-----|------|------|---------|--------|
| `POST /validate/rules` | 문서 텍스트 + 규칙 셋 ID | 규칙별 준수/위반 결과 | KAI 작성지침 기반 패턴 매칭 | 비교(규칙검사), K-Spec |
| `POST /extract/entities` | 요구사항 문장 | 대상장비, 성능수치, 시험조건, 적용규격 | 규칙 기반 NER + 정규표현식 | K-Spec, 비교 |

### 4.5 개발 순서 제안

1. 비교 서브시스템에서 필요한 분석 기능부터 먼저 구현 (현재 개발중이므로)
2. 단, 처음부터 독립 FastAPI 서비스로 설계 (비교 모듈 내부에 넣지 않음)
3. 비교 서브시스템은 HTTP로 문서 분석 API를 호출하는 구조
4. K-Spec 개발 착수 시, 같은 API를 그냥 호출하면 됨

## 5. 인제대 NLP 시스템 분석 (외부 기술 벤치마크)

### 5.1 개요

- **출처**: 인제대학교 산업경영공학과 최용선 교수
- **제목**: "NLP기반 정보추출기법을 이용한 규격서 관리 고도화 방안"
- **발표일**: 2025.12.24
- **원래 도메인**: 원전 정비 절차서 (KHNP, Exelon Generation 등)
- **KAI와의 관계**: 재료공정팀/공정개발팀이 문서 작성 검증 도구 필요성을 느껴 세미나 및 검증 의뢰

### 5.2 인제대 시스템 핵심 파이프라인

```
문서(Word/PDF)
    ↓
[A] 형태소 분석 / POS 태깅 (한국어+영어)
    ↓
[B] 의미 유형별 용어 추출 (장비/부품, 작업행위, 직무계통 등)
    ↓
[C] 문장 내 의미 컴포넌트 파싱
    (Condition → Action Verb → Target Object → Supporting Info)
    ↓
[D] 구조화 XML(XPML) 생성 + 정규화 DB 저장
    ↓
[E] 작성 지침 준수 검증 + 보고서 생성
    + 문서 간 참조관계 시각화
    + 대체 문구 제시 및 자동 교정
```

### 5.3 기능별 K-Spec 적용 가능성 분석

| 기능 | 인제대 수준 | K-Spec 필요성 | 자체 구현 | 비고 |
|------|-----------|-------------|---------|------|
| 형태소 분석/POS 태깅 | 한/영 모두, 자체 플러그인 | ★★★ | ★★★ 가능 | KoNLPy, Kiwi 등 오픈소스 |
| 도메인 용어 자동 추출 | 원전 용어집 기반 분류 | ★★★ | ★★☆ 부분 | 항공우주 용어집 별도 구축 필요 |

### 5.4 인제대 시스템 vs K-Spec 도메인 차이

**원전 절차서** (인제대 대상):
- 핵심 단위: "행위 지시문 (Action Step)" — "Ensure valve V1 is closed"
- 문장 유형: Action Step, Conditional Step, Continuous Action Step
- 검증 초점: 절차의 명확성, 안전성, Human Error 방지

**항공우주 규격서** (KAI 대상):
- 핵심 단위: "요구사항 서술문 (Requirement)" — "차폐 효과는 40dB 이상이어야 한다"
- 문장 유형: 요구(shall), 권고(should), 허용(may), 정보 서술, 시험 조건
- 검증 초점: 요구사항의 완전성, 일관성, 추적 가능성, 시험 가능성

→ **의미 컴포넌트 체계를 항공우주 규격서에 맞게 재정의해야 함**

6. **기술 스택 정합성**: 현재 프로젝트의 기술 스택과 섹션 3.3의 K-Spec 제안 기술 스택 사이에 충돌이나 불일치가 있는지 확인해 주세요.
