## 0. TL;DR — 결론 먼저

1. **"일반 문서 작성"만으로는 Author 를 독립 시스템으로 정당화하기 어렵다.** 그 능력은 **이미 Plan-60 으로 구현되어 Explorer 안에 들어가 있다**(Toast UI 마크다운 편집기 + Pandoc→DOCX 내보내기 + "작성 문서" 폴더). 그러므로 Author 를 "또 하나의 글쓰기 화면"으로 만들면 Explorer 와 정확히 중복된다 — 이것이 우려하신 역할 충돌의 실체다.

2. **Author 의 고유 가치는 Plan-24 의 "구조화 문서 합성(Structured Document Synthesis)"에 있다.** 여러 원문 스펙을 나란히 분석→비교→선별→초안 생성→검증으로 잇는 작업은 플랫폼 어디에도 없고, 시중 도구도(클라우드 한정) 폐쇄망·방산 도메인에선 대체재가 없다.

3. **권고 = Author 를 플랫폼의 "생산(창작)" 허브로 정의한다.** ① Plan-60 의 일반 저작을 Author 로 **승격·이관**해 "빈 문서 작성" 기본 모드로 삼고, ② 그 위에 Plan-24 의 "합성 작성" 모드를 얹는다. 그러면 **Explorer = 소비(읽기·검색·질의) / Author = 생산(쓰기·합성)** 으로 역할이 깨끗하게 갈린다.

4. 포맷·관리·내보내기는 **새로 설계할 필요가 없다.** Plan-60 이 확정한 **마크다운 SSOT + 통일 양식(reference.docx) + Pandoc DOCX + 소유권/soft lock** 을 그대로 계승한다. (근거·계층 구조는 §5)

> 즉 답은 "독립이냐 연동이냐"의 양자택일이 아니라 — **독립된 생산 공간이되, 입력은 Explorer/Notebook, 검증은 Verify 와 느슨하게 연동**되는 형태다.

## 1. 무엇을 정해야 했나 (요청 정리)

요청하신 질문은 네 가지로 압축된다.

- **실효성**: Author 가 독립 시스템일 만큼의 가치가 있나, 아니면 단순 에디터로 충분한가?
- **포맷·관리**: 어떤 포맷으로 작성·저장·공유·내보내기 하나?
- **레이아웃**: 업계 표준 화면 구성은 무엇이고 우리는 어떻게 잡나?
- **연동**: Explorer·Notebook·Verify 와 어떻게 엮나? (특히 **Explorer 와의 역할 구분**이 핵심 우려)

이 문서는 코드베이스에서 확인된 사실을 근거로 위 네 질문에 답한다.

## 2. 코드베이스가 말해주는 현실

### 2.1 플랫폼 구조와 제약

| 항목 | 내용 |
|------|------|
| 성격 | 폐쇄망(에어갭) 운용 · **Vanilla JS · 모놀리식 HTML · 무빌드** |
| 디자인 | 통일 블루 악센트(`#2c5282`/`#63a0e0`), `tokens.css` 변수 강제, 라이트/다크 |
| 런처 카드 | Explorer · Notebook · Verify(개발중) · **Author(개발 예정, 잠김)** |
| Author 카드 설명 | **"문서 작성 · 구조화 합성"** (`launcher.html` L218~222) |

런처 카드 문구 자체가 이미 **"구조화 합성"** 이라는 정체성을 암시하고 있다 — Plan-24 의 흔적이다.

### 2.2 Author 를 둘러싼 두 갈래의 계획

코드베이스에는 Author 에 대한 **서로 다른 두 비전**이 공존한다. 이 둘의 관계를 정리하는 것이 이번 작업의 핵심이다.

| | **Plan-24 (합성)** | **Plan-60 (저작)** |
|---|---|---|
| 제목 | Author 시스템 — 구조화 문서 합성 워크벤치 | 통일 양식 기반 문서 저작·내보내기 |
| 작성/상태 | 2026-04 · **icebox(보류)** | 2026-06 · **활성, 대부분 구현 완료** |
| 핵심 | 다중 스펙 비교→선별→AI 초안→Verify 검증 | 마크다운 편집기 + DOCX 내보내기 |
| 산출물 위치 | (미구현) | **Explorer 안(`index.html`)에 통합됨** |
| 콘텐츠 모델 | 프로젝트(소스+매트릭스+초안) | 마크다운 `.md` SSOT |
| 비유 | "리뷰·합성 워크벤치"(Covidence류) | "사내 위키/저작툴"(GitHub·Notion류) |

### 2.3 문제의 핵심 — Plan-60 이 이미 Explorer 안에 "글쓰기"를 넣었다

Plan-60 은 단순 계획이 아니라 **이미 돌아가는 기능**이다 (커밋 `cddc377`·`d44e7c1` push 완료):

- `index.html`(Explorer)에 Toast UI 마크다운 편집기 로드 (`js/md-editor.js`, `css/md-editor.css`)
- "새 문서" 버튼 → 풀스크린 모달 편집기 → `POST /api/save-markdown` → `contents/authored/*.md`
- 통일 양식 골격 프리필(개요/배경/목적/본론/결론) + front matter(제목·작성자·문서번호·보안등급)
- "DOCX 내보내기" 버튼 → Pandoc(MD→HTML→DOCX) + reference.docx + 표지 후처리
- `GET /api/authored` → 좌측 트리에 "작성 문서" 가상 폴더 자동 노출

**결과: 플랫폼은 이미 "웹에서 글을 써서 공유·발행"할 수 있다 — 단, 그 입구가 "탐색" 시스템인 Explorer 안에 있다.**

이것이 우려하신 "Explorer 와 Author 의 역할 충돌"의 정체다. Author 를 그냥 "글쓰기 시스템"으로 열면 Plan-60 과 100% 겹친다. **Author 가 살아남으려면 Plan-60 이 못 하는 일을 해야 하고, 동시에 Plan-60 의 저작 기능이 "탐색" 시스템에 얹혀 있는 어색함도 풀어줘야 한다.**

## 3. 실효성 판단 — Author 는 독립 시스템일 가치가 있나

세 가지 시나리오를 놓고 평가했다.

### 시나리오 A — "합성 전용" Author (Plan-24 그대로)
Author = 다중 스펙 합성 워크벤치만. 일반 저작은 Explorer(Plan-60)에 그대로 둔다.

- 👍 역할이 가장 뾰족함. 시장 공백(구조화 합성)에 정확히 대응.
- 👎 런처 카드의 "문서 작성" 문구·사용자 의도("우선 문서작성 목적")와 어긋남. 일반 저작이 "탐색" 시스템에 남는 어색함 미해결.

### 시나리오 B — "생산 허브" Author (권고) ⭐ — **사용자 채택 (2026-06-18)**
Author = **빈 문서 작성(Plan-60 승격) + 합성 작성(Plan-24)** 을 모두 품는 생산 공간. Explorer 는 순수 소비로 환원.

- 👍 **Explorer/Author 역할이 깨끗하게 분리됨**(소비 vs 생산). 런처 카드·사용자 의도와 일치. Plan-60 자산을 100% 재활용. 두 모드가 같은 MD SSOT·통일 양식·DOCX 내보내기로 수렴.
- 👎 이미 Explorer 에 박힌 편집기 진입점을 Author 로 옮기는 이관 작업 필요(단, 백엔드·편집기 코드는 그대로).

### 시나리오 C — "Author 폐기" (독립 에디터로 Explorer 잔류)
Author 카드를 접고, 글쓰기는 Explorer 안 기능으로 영구 유지.

- 👍 추가 개발 0. 가장 적은 비용.
- 👎 합성이라는 **실수요(엑셀 수작업 5시간→1시간, Plan-24 §1)** 를 영영 못 채움. 런처에 광고된 Author 를 철회하는 후퇴. "탐색 시스템 안의 글쓰기"라는 개념적 부채 잔존.

### 업계 근거 (2026)

- **docs-as-code / single-source authoring**: 마크다운 원본 1벌 → 웹·DOCX·PDF 다중 출력은 GitHub·GitLab·Confluence·MkDocs·Docusaurus 가 수렴한 표준. (Plan-60 내부 deep-research 22소스 교차검증)
- **AI 문서 생성·합성**: ML Clever·LlamaIndex·Hebbia 등 2026 도구가 "구조·근거·거버넌스를 갖춘 문서 생성"과 "다중 소스 동시 분석으로 공통점·상충·합성 기회 식별"을 핵심으로 내세움 — **Plan-24 의 합성 워크플로우가 시장 주류 방향과 일치**함을 확인. 단 전부 클라우드 → **폐쇄망·방산 표준(MIL-STD 등) 도메인엔 빈자리**.
- **구조화 리뷰 도구**: Covidence(체계적 문헌고찰)가 "여러 소스를 한 화면에서 비교·추출·판정"하는 워크벤치의 좋은 형태적 참조.

**판정: 시나리오 B 권고 → 사용자 채택.** 합성(고유 가치)을 살리되, 일반 저작도 Author 로 모아 Explorer 와의 역할을 정리하는 것이 실효성·일관성·비용 모두에서 우월하다.

## 4. 권고 컨셉 — Author = 플랫폼의 "생산(창작)" 허브

### 4.1 정체성 — 사분면 모델 (Plan-24 §1.3 계승, 갱신)

```
┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│ Explorer │  │ Notebook │  │  Verify  │  │  Author  │
│ 소비(읽기)│  │ 내재화    │  │ 검증(판단)│  │ 생산(창작)│
│ 탐색·검색 │  │ 번역·분석 │  │ 비교·유사 │  │ 저작·합성 │
│ AI 질의  │  │ 지식관리  │  │ 규칙검증  │  │ 초안생성  │
└────┬─────┘  └────┬─────┘  └────┬─────┘  └────┬─────┘
     │ 입력 소스 ───┴──────────────┘            │
     └──────────────────────────────→ 검증 왕복 ┘
        Explorer/Notebook 문서 = Author 의 입력
        Author 초안 = Verify 의 입력 / Explorer 의 발행물
```

한 문장: **Explorer 는 "남이 쓴 문서를 읽는 곳", Author 는 "내가 새 문서를 만드는 곳".**

### 4.2 Author 의 두 진입 모드

| 모드 | 무엇 | 출처 | 누구 |
|------|------|------|------|
| **① 빈 문서 작성** | 통일 양식 골격에서 새 기술 보고서를 마크다운↔WYSIWYG 로 작성 | Plan-60(승격) | 일반 엔지니어, 일상 문서 |
| **② 합성 작성** | 원문 스펙 2~5개 → AI 추출 → 비교 매트릭스 → 선별 → AI 초안 | Plan-24(신규) | 규격 제정·표준화 담당 |

두 모드는 **같은 출구로 수렴**한다: 마크다운 `.md` (SSOT) → 통일 양식 → DOCX 내보내기 → 검증·발행.
즉 합성 모드의 "초안"이 곧 저작 모드의 "문서"가 되어, 한 편집기·한 양식·한 내보내기 파이프라인을 공유한다.

### 4.3 Explorer 역할 재정리 (역할 충돌 해소)

- **이관**: 현재 Explorer 안의 "새 문서"·"작성 문서" 진입을 **Author 로 이동**. 편집기 엔진(`md-editor.js`)·백엔드(`/api/save-markdown`·`/api/export-docx`)·양식은 그대로 재사용 — UI 진입점만 Author 로 옮기는 저비용 이관.
- **잔류**: Explorer 는 기존 변환 웹북(Monaco/HTML) 열람·검색·RAG 질의에 집중. 작성된 `.md` 는 발행되면 Explorer 트리에 **읽기 대상**으로 노출(생산물의 소비처).
- **이행 안전장치**: Plan-60 의 "교체 아닌 추가" 원칙과 동일하게, 이관 후에도 백엔드 계약 불변 → 회귀 위험 최소.

## 5. 포맷 · 관리 방식

### 5.0 결정 요약 (Plan-60 / 통일 양식 사양 v0.3 계승)

| 항목 | 결정 |
|------|------|
| **콘텐츠 SSOT** | 마크다운 `.md`. HTML(웹 서빙)·DOCX(제출본)는 파생 출력 |
| **편집기** | 드롭인 마크다운(Toast UI, 자가호스팅 번들) — 마크다운↔WYSIWYG 토글. 무빌드·MIT·폐쇄망 적합 |
| **양식** | 통일 양식 = `reference.docx` **파일 1벌**(코드 아님). 회사 양식 확보 시 파일 교체만으로 적용 |
| **메타** | YAML front matter: `title`·`author`·`date`·`doc_number`(문서번호)·`classification`(보안등급) |
| **구조 골격** | 개요/서론·배경/본론/결론 [+부록] 프리필. 누락 시 강제 아닌 경량 경고 |
| **내보내기** | `MD → (Pandoc) HTML → (Pandoc + reference.docx) DOCX → 표지 후처리(python-docx)` → 워드에서 다듬어 제출 |
| **동시편집** | soft lock(편집중 표시 + 낙관적 저장검사 ETag) + **담당자 소유권**(소유자 1인·편집권·위임·관리자 재지정) |
| **권한** | 전역 RBAC(viewer/editor/admin) 계승. editor/admin 만 작성 |

### 5.1 왜 마크다운을 "정본"으로 두는가 (포맷 근거)

최신 협업 문서 플랫폼(Notion, Google Docs, TipTap/ProseMirror 계열)은 **블록 단위 구조화 모델(JSON)** 을 정본으로 두고 MD·HTML·PDF 를 파생 출력으로 다룬다. 이상적이지만 **우리 환경에선 채택 불가** — 그 방식이 전제하는 세 가지(① 배포 전 **빌드/번들 조립**, ② 의존성 수급용 **네트워크**, ③ 실시간 병합용 **동기화 서버**)를 본 플랫폼이 **의도적으로 모두 배제**했기 때문이다(무빌드·폐쇄망·실시간 협업 제외, Plan-60 §7).

세 포맷을 본 플랫폼 제약 기준으로 비교하면:

| 기준 | 마크다운(MD) | HTML 통일 | 블록 JSON(Notion식) |
|------|:---:|:---:|:---:|
| 웹 표현력 | 중 (표·수식 보강) | **상** | 상 |
| 이식성·diff·git | **상** | 하(태그 노이즈) | 하(전용 포맷) |
| RAG/검색 친화 | **상**(텍스트 근접) | 중(태그 제거 필요) | 중 |
| 저작 난이도 | **낮음** | 높음(전문가용) | 낮음(단 에디터 무거움) |
| 무빌드·폐쇄망 적합 | **적합** | 적합 | **부적합** |
| 통일 양식 강제 | 쉬움(양식=출력단계) | 어려움(문서마다 스타일 혼입) | 중 |

- **왜 HTML 통일이 아닌가**: HTML 은 *표현* 포맷이지 저작·저장 정본으로 약하다. 손 편집이 전문가용이라 Plan-60 이 Monaco-HTML 에서 벗어난 이유 그 자체이고, WYSIWYG 왕복 시 구조가 깨지며, diff 가 태그 노이즈로 지저분하고, 내용·스타일이 섞여 통일 양식을 문서마다 다시 박아야 한다. 무엇보다 **Plan-25 가 Explorer 를 HTML→PDF+MD 로 옮기기로 이미 결정**했다 → HTML 통일은 자체 로드맵 역행.
- **왜 블록 JSON 이 아닌가**: 빌드·DB·전용 렌더러 유지보수 + 벤더 락인. 무빌드·폐쇄망 위반. (§5.1 첫 문단 참조)
- **그래서 MD 정본이 옳다**: 무빌드·이식성·diff·RAG 정합 + docs-as-code 표준. "웹 표현력 약함"은 **MD 안에 필요한 만큼만 HTML 섬을 허용**해 메운다 — 단순 표=파이프표, 병합표=raw `<table>`, 수식=LaTeX, 메타=front matter (통일 양식 사양 §1·§4).

### 5.2 "일원화 위반" 우려에 대한 답 — 정본 1개 → 파생 렌더 계층

일원화의 기준은 **"파일 포맷 1개"가 아니라 "문서당 정본 1개 + 파생 렌더"** 다. 이 관점에서 보면 플랫폼은 이미 사실상 일원화돼 있다.

```
            ┌───────────────────────────────────────┐
            │     정본 (SSOT) = 문서당 1개 소스      │
            │   · Author 신규 = Markdown(.md)        │
            │   · Explorer 레거시 = HTML (→ MD 수렴 예정, Plan-25) │
            └───────────────────┬───────────────────┘
                                │  (한 정본에서 갈라짐)
      ┌─────────────────────────┼─────────────────────────┐
      ▼                         ▼                         ▼
┌───────────┐           ┌───────────────┐         ┌──────────────┐
│ 렌더(웹)  │           │ 텍스트/인덱스  │         │ 내보내기      │
│ marked +  │           │ html_to_text  │         │ Pandoc +      │
│ DOMPurify │           │ → BM25/FAISS  │         │ reference.docx│
│ → HTML    │           │ → RAG·검색    │         │ → DOCX 제출본 │
└───────────┘           └───────────────┘         └──────────────┘
   화면 표시              챗봇·검색 (포맷 무관)        워드 다듬기

구조 메타는 별도 JSON 사이드카로 분리 (Plan-25 3계층: 표현=PDF/콘텐츠=MD/구조=JSON)
```

- **검색/RAG 레이어**: Explorer(HTML)든 Author(MD)든 결국 plain text 로 추출되어 동일 인덱스로 들어간다 → **인덱싱은 포맷 무관**.
- **렌더 레이어**: 둘 다 브라우저에선 HTML 로 그려진다.
- **소스 레이어**만 현재 둘(HTML 레거시 + MD 신규)이며, **Plan-25 가 이를 MD 로 수렴**시키는 계획을 이미 보유 → 완전 일원화는 로드맵상 예정된 수순.
- 이 구조는 Notion 의 "JSON 정본 + 다중 파생"과 **같은 철학**이며, 정본을 (빌드가 필요한)JSON 대신 **MD 로 둔 것**이 무빌드·폐쇄망에 맞는 우리식 선택이다.

> **열린 결정 1건**: Explorer 레거시 HTML 을 언제 MD 로 수렴시켜 소스 레이어까지 완전 일원화할지(Plan-25 Phase 1). Author 개편과 별개 트랙으로 논의.

### 5.3 합성 모드의 추가 데이터 (Plan-24 계승)

합성 모드는 위 구조에 **프로젝트 영속 구조**만 더한다: `data/author/{user}/{project}/` 에 `meta.json`·`sources/`·`extraction.json`·`matrix.json`·`draft.md`. 초안(`draft.md`)이 발행되면 일반 저작 문서와 동일하게 `contents/authored/` 로 승격 → 그 순간부터 §5.2 의 정본→파생 흐름에 합류.

## 7. 기존 시스템 연동 설계

| 연동 | 방향 | 방식 | 근거 인프라 |
|------|------|------|------------|
| **Explorer → Author** | 입력 | 탐색 중 문서를 합성 소스로 "가져오기" | Plan-25 문서 직접 참조 패턴 |
| **Notebook → Author** | 입력 | 번역·추출된 `.md`(`full_extracted.md`)를 소스로 | Plan-25/26 MD 파이프라인 |
| **Author → Verify** | 검증 | 초안 + 소스 → 유사도(표절)·규칙 검증 → 결과 표시 | Plan-24 §4.4, URL/sessionStorage |
| **Author → Explorer** | 발행 | 완성 `.md` → `contents/authored/` → 트리 노출(읽기) | Plan-60 `GET /api/authored` |
| **공통 데이터** | — | MD(콘텐츠)+JSON(구조) 표준 구조로 사일로 해소 | Plan-25 document-centric |

**연결 철학 = 느슨한 결합.** Verify/Notebook 연계는 하드 의존이 아니라 URL/API 기반(Plan-24 §9-5). 한 시스템이 죽어도 Author 의 핵심(작성·합성)은 동작.

이 설계가 우려하신 "독립 vs 연동" 질문의 답이다 — **Author 는 독립 실행 가능한 생산 공간이지만, 입력(Explorer/Notebook)과 검증(Verify)에서 플랫폼과 자연스럽게 맞물린다.** 연동이 없어도 Author 단독으로 가치가 있으므로(빈 문서 작성), 연동 실효성이 약한 부분은 후순위로 미뤄도 안전하다.

---

## 8. 독립 vs 연동 — 결론

> **"독립된 생산 공간 + 선택적 연동"** 이 정답이다.

- **독립성**: Author 는 그 자체로 "새 문서를 만드는 곳"이라는 완결된 정체성을 가진다. Explorer/Notebook/Verify 가 없어도 빈 문서 작성·DOCX 내보내기는 동작한다.
- **연동성**: 합성 모드의 소스 수급(Explorer/Notebook)과 검증(Verify)은 플랫폼 시너지의 핵심이지만 **하드 의존이 아니다.** 단계적으로 붙인다.
- 따라서 "연동 실효성이 없으면 독립 에디터로 유지"라는 가설은 **부분적으로만 맞다** — 연동이 약해도 Author 는 살아야 한다. 다만 그 형태는 "Explorer 안의 에디터"가 아니라 "독립된 생산 시스템"이어야 역할이 깨끗하다.
