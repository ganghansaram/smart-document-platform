### 핵심 변경 (엔진)

```python
caption_id = self._detect_caption(text, paragraph)          # 참조 캡션 — 무변경
id_attr = f' id="{caption_id}"' if caption_id else ''       # id 는 참조 캡션에만
is_caption = bool(caption_id) or (
    tag == 'p' and self._is_display_caption(text))          # 표시 캡션 — 신설
```

`tag == 'p'` 가드는 사전 분석에서 발견한 JS 와의 비대칭을 막는다 — JS 는
`querySelectorAll('p')` 로 `<p>` 만 훑지만 엔진은 `h1~h6` 도 지난다.

## 5관점 피드백

**개발책임자** — 계획서의 "표시/의미 분리" 판단이 실측으로 검증됐다. 특히 사전 분석에서
**fingerprint 가 속성 변화를 못 잡는다**는 걸 먼저 확인한 게 컸다. 그걸 몰랐다면
"테스트 통과"를 안전의 증거로 오독했을 것이다. 회귀 방어망은 그 구멍을
`test_caption_tiers.py` 로 메웠다.

**코드전문가** — 삽입 지점 4줄, 신규 함수 1개. 파일에 이미 `Tier 1~4`(heading 캐스케이드)가
있어 코드에서는 "참조/표시 캡션" 용어를 썼다 — 계획서 용어를 그대로 옮겼다면 혼선이
생겼을 자리다. `_is_display_caption` 이 `self` 를 안 쓰지만 `_detect_caption` 과의
대칭을 위해 인스턴스 메서드로 뒀다.

**UI/UX 전문가** — 캡션이 대상에 붙으면서 "이 캡션이 무엇의 캡션인가"가 시각적으로
분명해졌다. 그림 아래 캡션까지 대칭 처리(B안)해 표/그림 규칙이 화면에서 일관되게 읽힌다.

**웹디자인 전문가** — `.caption + p > img` 를 `:has(> img)` 로 바꾼 게 핵심이다. 마진 주체가
아닌 요소에 마진을 걸던 규칙이라, Explorer 는 전역 리셋에 가려 우연히 동작하고 웹북은
깨지는 상태였다. `.caption + p` 로 넓히지 않은 이유는 캡션 뒤 **본문** 문단까지 4px 를
받아 의도치 않게 압축되기 때문이다.

**사용자** — 업체는 exe 교체만 하면 된다(CLI 인자·호출 방식 불변). 전달 README 에 실측
before/after 표를 넣어 "무엇이 좋아졌는지"를 숫자로 확인할 수 있게 했다.

## 업계표준 재검토

**조사** — HTML 표준에는 캡션-대상 결합 수단이 이미 있다: 표는 `<table><caption>`,
그림은 `<figure><figcaption>`. 둘 다 DOM 인접이 아니라 **부모-자식 구조**로 묶이므로
사이에 무엇이 끼든 결합이 깨지지 않고, 스크린리더가 캡션을 대상과 연결해 읽는다.

**비교** — 현 구조는 `<p class="caption">` + 형제 인접 CSS 에 의존한다. 접근성 정보가
없고, 문단 하나만 끼어도 결합이 끊어진다. 시맨틱하게는 열등하다.

**판단** — 이번 범위에서는 채택하지 않았다. `<figure>` 전환은 (a) 변환기 출력 구조 변경,
(b) `figure-popup.js` 의 인접 탐색(±3 형제) 로직 재작성, (c) 이미 등록된 `contents/*.html`
전량 재변환, (d) 업체 웹북의 기존 콘텐츠까지 영향 — 계획서가 명시적으로 제외한
"구조 변경" 범주다. **수용한 한계**: 접근성 개선과 결합 견고성은 미해결로 남는다.
후속 계획서 후보로 기록한다.

## 🔴 자체 검토에서 잡은 결함 — `:has()` 셀렉터 그룹 (2026-07-29)

**내가 만든 결함이다.** `:has()` 를 핵심 규칙 그룹 안에 넣었는데, CSS 는 셀렉터
그룹에 못 읽는 셀렉터가 **하나라도** 있으면 **규칙 전체를 폐기**한다.

```css
/* 결함 버전 */
.docx-content .caption + table,          /* ← :has() 미지원 시 */
.docx-content .caption + p:has(> img),   /* ← 이것 때문에 */
.docx-content .caption + .figure-wrap { margin-top: 4px; }   /* ← 전체 폐기 */
```

`:has()` 는 Chrome/Edge **105+** 필요. **전자정부 기반 웹북**은 구형 브라우저
가능성이 있고, 그 경우 **보고된 증상이 v1.5.0 보다 나빠진다** — v1.5.0 은 이 그룹에
`:has()` 가 없어 안전했다.

### 실측 (`:has` → `:unsupported-has` 치환으로 구형 브라우저 시뮬레이션)

| 케이스 | 구형·규칙분리 전 | 구형·규칙분리 후 | 최신 |
|--------|---------------:|---------------:|-----:|
| **캡션 → 표 (핵심 증상)** | **24px** 🔴 | **4px** ✅ | 4px |
| 캡션 → 이미지표 | 16px | 16px | 4px |
| 그림 → 캡션 | 16px | 16px | 4px |

### 조치

`:has()` 를 쓰는 셀렉터를 **전부 독립 규칙으로 분리**했다 (CSS 3파일).
구형 브라우저에서는 이미지 관련 규칙만 조용히 무시되고 표 규칙은 살아남는다 —
우아한 열화이며 v1.5.0 대비 악화 없음.

### 교훈

`:has()`·`:is()` 같은 신규 셀렉터는 **기존 셀렉터와 같은 그룹에 넣지 않는다.**
v1.5.0 이 우연히 안전했던 이유도 `:has()` 규칙이 독립돼 있었기 때문이다.
`css/content.css`·`webbook-content.css` 에 주석으로 남겼다.

### 동일 패턴 전수 점검 → 기존 결함 1건 발견·수정

프로젝트 CSS 전체를 스캔해 `:has()` 와 일반 셀렉터가 섞인 규칙을 찾았다.

| 파일 | 상태 |
|------|------|
| `css/platform-footer.css:42` | 🔴 **기존 결함** — `.launcher-main ~ .platform-footer, body:has(.launcher-main) …` 혼재 → 분리 |
| 그 외 전체 | 0건 |

> 실제 체감 영향은 작았다 — `launcher.html:167` 의 인라인 `!important` 가 색을 덮고
> 있어 구형 브라우저에서도 대부분 가려졌다. 그래도 분리가 정확한 형태다.
