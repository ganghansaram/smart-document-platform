## 1. 업계 표준 재조사 — **라벨이 아니라 구조**

### 1.1 Turnitin 2024+ (Match Groups 신규)

Turnitin은 2024년에 분류 체계를 전면 개편했습니다. **인용 컨텍스트 기반 4그룹**:

| 그룹 | 의미 | 사용자의 행동 |
|---|---|---|
| **Not Cited or Quoted** | 출처·인용 표기 없음 | "출처를 밝혀라" |
| **Missing Quotations** | 출처는 있으나 인용부호 없음 | "큰따옴표 추가" |
| **Missing Citation** | 인용부호는 있으나 출처 없음 | "출처 추가" |
| **Cited and Quoted** | 정상 인용 | "OK, 확인만" |

**핵심 인사이트**: Turnitin의 그룹은 "유사도 강도"가 아니라 **"사용자가 무엇을 해야 하는가"** 기준으로 나뉜다. 각 그룹 이름 자체가 **행동을 지시**한다 ("Missing" = 추가해라, "Cited" = 그대로 둬라).

**Turnitin 공식 권장 워크플로우**: "Not Cited 먼저 고치고 → Missing Quotations → Missing Citation 순서"로 처리. 즉 그룹이 **작업 순서의 축**이다.

### 1.2 Copyleaks (단순 3단계)

유사도 강도 3단계 (Identical / Minor Changes / Paraphrased). 그룹이라기보다 **스펙트럼**. 필터는 강도 레벨 토글.

### 1.3 iThenticate (출처별 그룹)

Turnitin과 IA 공유하되, 보조축으로 **출처별 그룹핑**. 즉 "이 출처에서 23% 매칭" 단위로 본다.

### 1.4 카피킬러 (혼합)

"표절의심 / 인용 / 법령·경전 / 일반" — 강도(표절의심)와 컨텍스트(인용/법령)를 섞음. 한국 학술계 특유의 "법령·경전 제외" 규칙이 축 하나로 들어감. **우리 4그룹이 이 모델을 모방한 것**.

### 1.5 결정적 차이

**Turnitin/Copyleaks는 "한 축"이 명확**. 축이 혼합된 것은 카피킬러(한국 학술)뿐이고, 이마저도 **사용자가 한국 학술계 관행에 익숙**하다는 전제가 있다.

**우리 시스템은 카피킬러를 따라 했는데, 사용자는 K-SPEC 기술자(MIL-STD 표준서를 보는 엔지니어)다. 이들에게 "인용/법령·경전" 어휘는 낯설다.** 그래서 "표절 의심 / 참고 가능 / 제외 영역 / 일반"으로 번역했지만, 번역 결과는 **어느 축인지 애매**해졌다:

- "표절 의심" = 강도 높음?
- "참고 가능" = 약한 유사? 아니면 "참고해도 되는(OK) 영역"?
- "제외 영역" = 자동 제외? 수동 제외? 둘 다?
- "일반" = 매칭 없음 (카테고리 구성원 0개)

**즉 우리 4그룹은 의미 축이 혼란하고, 그 이름들이 행동을 지시하지도 않는다.**

## 2. Plan-38의 구조적 결함 — 나의 재해석

Plan-38이 "분류 축을 하나로" 못 했던 이유를 역추적하면:

### 2.1 단일 축 = 여러 목적의 병합

한 축으로 다음을 모두 커버하려 했습니다:
1. **색상 하이라이트** (본문에서 시각 구분)
2. **필터 컨트롤** (사용자 토글)
3. **점수 산출 공식** (가중치 계산)
4. **통계 바** (분포 시각화)
5. **보고서 섹션** (출력 구조)

**문제**: 이 5가지 목적은 **최적 축이 다릅니다**:

| 목적 | 최적 축 | 이유 |
|---|---|---|
| 본문 하이라이트 | 6세부(세밀) | 색상 정보량 많을수록 좋음 |
| 필터 컨트롤 | 행동 기반(3~4) | 토글 수 ≤7개, 사용자 의도 축 |
| 점수 공식 | 3분(실질/가중/제외) | 수식 구조와 일치 |
| 통계 바 | 4그룹(묶음) | 한눈에 파악 |
| 보고서 | 행동 기반(3~4) | 회람자 설명 가능 |

**Plan-38은 5가지 모두를 4그룹+6세부로 밀어 넣었다.** 그래서 어딘가에서는 반드시 어긋난다.

### 2.2 "제외 영역"의 의미 과부하

"제외 영역"이라는 한 카테고리에:
- 백엔드 자동 제외 (boilerplate/TOC/caption/references/spec_number) — "알고리즘 판단"
- 사용자 수동 제외 — "사람 판단"

이 둘은 **근본적으로 다른 성격**입니다. Gmail이 "스팸" vs "휴지통"을 구분하고, GitHub이 "resolved" vs "hidden"을 구분하는 이유. 합쳐두면 "왜 여기 있지?"가 설명 안 됨.

### 2.3 "일반"의 허상

"일반(clean) = 매칭 없는 문장" — 매칭 카드가 **존재하지 않음**. 필터 토글도 무의미, 통계 바에서 큰 회색 영역만 차지. 사용자는 "일반 217"을 보고 "217건의 일반 매칭이 있나?"로 오독. 분모일 뿐인데 카테고리로 표현됨.

## 3. 사용자 워크플로우 관점 — 재구성

K-SPEC 검토자의 실제 작업 흐름:

```
1. 유사율 확인 → "우리 문서가 안전한가?"
2. 매칭 리스트 훑기 → "문제될 게 있나?"
3. 매칭별 판단:
   a. 진짜 차용이면 → 다시 쓰기 또는 출처 명시
   b. 정당한 참조면 → 그대로 두되 "판단 완료" 표시
   c. 표준 문구라 의미 없음 → 자동으로 걸러짐 (사용자는 확인만)
4. 보고서 출력 → 부서 회람
```

**이 워크플로우에서 사용자가 필요한 UI**:
- "아직 판단 안 한 매칭" 목록 (액션 필요)
- "내가 판단한 매칭" 목록 (기록)
- "시스템이 자동 처리한 매칭" 목록 (검증 목적, 선택적)

**행동 기반 3그룹**:

| 그룹 | 의미 | 사용자의 다음 행동 | 기본 표시 |
|---|---|---|---|
| 🔴 **검토 필요** | 백엔드가 자동 제외 못 한 유의미 매칭 (identical/near_copy/paraphrase/translation/low_sim) | 1건씩 판단 | ✅ 기본 노출 |
| ⚪ **자동 제외** | 백엔드 자동 걸러짐 (boilerplate/TOC/caption/refs/spec) | 검증 (대부분 넘어감) | ❌ 기본 숨김 |
| ✓ **판단 완료** | 사용자가 수동 제외한 매칭 (false positive 판정) | 기록, 필요 시 복원 | ❌ 기본 숨김 |

**Turnitin 모델 + 우리 도메인**: 축이 "사용자의 다음 행동"으로 통일됨. 각 그룹 이름이 **행동을 지시**.

**점수 계산은 별도 축**: 그룹과 독립적. "검토 필요" 그룹에서도 6세부(일치/거의 동일/의역/번역/약한 유사)가 점수에 다르게 기여. 이는 **카드 내부 정보**로만 노출.

## 4. 세 가지 방향 (옵션)

### 옵션 A — **표층 수정** (Plan-45 원안대로 진행)

- Plan-38의 4그룹 유지 (표절 의심 / 참고 가능 / 제외 영역 / 일반)
- 라벨 축약 금지, SSOT 통일, 가시성 게이트 단일화
- **공수**: 2.9~3.9일
- **장점**: 기존 Plan-38 작업 보존, 낮은 리스크
- **단점**: "제외 영역" 의미 과부하, "일반" 허상 그대로, 축 혼합 근본 원인 미해결
- **결과 예상**: 사용자가 6개월 후 "다시 혼란스럽다"고 할 가능성 **중~높음**

### 옵션 B — **축 재정의** (권장)

- 4그룹 → **행동 기반 3그룹**으로 재명명
  - 표절 의심 + 참고 가능 → **"검토 필요"** (통합, 6세부는 카드 내부)
  - 제외 영역 → **"자동 제외"** (사용자 판단과 분리)
  - (신규) → **"판단 완료"** (사용자 수동 제외만)
  - "일반"은 카테고리에서 제거 (누적바에서만 회색 배경으로 표현)
- 필터 UI: 3탭 (Turnitin 스타일) 또는 3체크박스
- 점수 산출: 내부 6세부 그대로 유지 (백엔드 불변)
- SSOT 갱신 (`similarity-help.json` `groups` 섹션 재구조화)
- **공수**: 4~5일 (SSOT·가이드·보고서·모달·L3 페이지 전면 수정 포함)
- **장점**: 축 명확, 행동 지시, 유지보수 단순화, 업계 최신 패턴
- **단점**: Plan-38 L3 가이드 페이지·모달 A/B/C 재작성 필요, similarity-help.json 버전 업 (v1→v2)
- **결과 예상**: 사용자 학습 곡선 개선, 장기 안정

### 옵션 C — **단일 축 유지 + 다축 공존** (중도)

- 필터는 **6세부** (Copyleaks 모델 — 강도 단일 축)
- 통계 바는 누적 비율만 (카테고리 아닌 분포)
- "제외 영역"/"일반" 카테고리 명칭 폐지
- 점수·색상·필터·통계 모두 6세부 축 하나로
- **공수**: 3~4일
- **장점**: 가장 단순, 카테고리 이름 정의 문제 없음
- **단점**: 6세부 중 "translation"·"boilerplate" 같은 희귀 유형 필터 UX 번잡, 한국 사용자에게 "카테고리 없음"이 어색
- **결과 예상**: 엔지니어 관점은 깔끔하나 한국 사용자 UX는 거친 편

## 6. 권고

근거:
1. **문제 진단이 "라벨"이 아니라 "분류 체계 자체"**였음이 재검토로 확실해짐

1. **그룹 명칭**: "검토 필요 / 자동 제외 / 판단 완료" 이 3개로 확정? 아니면 대안?
2. **UI 형식**: Turnitin식 탭 vs 현재식 체크박스. (기술 문서 리뷰어는 탭이 자연스러울 가능성 — 한 번에 한 종류 집중)
3. **마이그레이션 범위**: `similarity-help.json` v1→v2 전환, 기존 export·리포트 라벨 전면 갱신 — 단일 PR 또는 2단계 분할?

## 7. 왜 이번엔 다를 것인가 — 실패 방지책

Plan-38이 실패한 메커니즘을 분해하면:

1. **원칙 부재**: "라벨은 SSOT 경유" 같은 강제 규칙이 명시만 되고 강제 안 됨 (구현 단계에서 리터럴 슬쩍 들어감)
2. **검증 부재**: "모든 라벨이 SSOT 경유인지" 자동 검증 테스트 없음
3. **축 혼합 무자각**: 4그룹과 6세부를 섞어 쓰는 게 설계 의도임을 구현자가 놓침

**옵션 B에서 이를 막으려면**:

| 실패 모드 | 방지 메커니즘 |
|---|---|
| 라벨 리터럴이 섞임 | `compare.html`·`export_service.py`에 **grep 테스트** 추가 ("표절 의심"/"검토 필요" 등 그룹 라벨이 SSOT 외 등장 0건) |
| 축 혼합 재발 | 그룹 개수 ≠ 세부 개수임을 사이드바 CSS 그리드로 **구조적 분리** (한 그리드에 섞여 들어갈 수 없게) |
| 새 기능이 그룹 개념을 몰라서 재해석 | `CLAUDE.md`에 "유사도 3그룹 = 검토 필요/자동 제외/판단 완료" 명시 |
| 점수 공식과 UI 그룹이 엮임 | 점수 공식은 **세부 유형 기반**이고 **그룹과 독립**임을 코드 주석·문서에 명시 |

## 8. 결정 필요 사항 (지금 논의)

1. **방향**: 옵션 A / B / C 중 어느 것?
   - 시간 제약이 크면 → A (단, 6개월 내 재작업 감수)
