## 1. 프로젝트 개요

### 1.1 발전 경과

본 프로젝트는 "KF-21 개발 백서 열람용 웹북" 시범 시스템으로 시작하여, 약 1개월 만에 기술 문서 활용 플랫폼으로 확장되었다.

```
Phase 1 (완료)  : 정적 웹북               → "읽는 시스템"
Phase 2 (완료)  : RAG + 편집기            → "활용하는 시스템"
Phase 3 (완료)  : 관리 기능 + 통계         → "운영하는 시스템"
Phase 4 (완료)  : 비교/번역/다중 시스템     → "기술 문서 활용 플랫폼"
Phase 5 (진행중) : 품질 향상 + 지식 저장소   → "지식 활용 플랫폼"
```

### 1.2 핵심 제약

- **에어갭 환경**: 외부 인터넷 차단, 모든 구성요소 자체 호스팅
- **Vanilla JS + 모놀리식 HTML**: 프레임워크/빌드 시스템 없음
- **사용자**: 설계/품질/공정 엔지니어 (비개발직군)
- **PDF DRM**: 사내 PDF는 일정 시간 후 DRM 적용 → 번역 결과 다운로드 필수

## 3. 궁극적 목표

### 3.1 비전

> **"폐쇄망 엔지니어를 위한 개인 지식 플랫폼"**
>
> NotebookLM의 AI 문서 이해 + Obsidian의 로컬 지식 관리를 결합하되,
> **폐쇄망 동작**과 **외국어 기술문서 번역**이라는 경쟁 제품에 없는 차별점을 갖는다.

### 3.2 현재 → 목표

| 현재 | 목표 |
|------|------|
| Explorer: 문서 탐색 도구 | **지식 허브** — 문서 업로드 → AI가 이해 → 검색/질의/요약 |
| Translator: PDF 번역 도구 | **개인 지식 저장소** — 번역 + Markdown 웹 뷰 + 챗봇 + 문서 연결 |
| Compare: 문서 비교 도구 | **문서 품질 게이트** — 비교 + 규칙 검증 + 변경 분석 |
| (없음) | **K-Spec** — 표준 기술문서 제정/관리 시스템 |
| (없음) | **문서 분석 서비스** — 공통 NLP/파싱 API 레이어 |

### 3.3 사용자 피드백 및 경영층 방향

**테스트 참여 동료들의 요청:**
- Translator를 **개인 문서 저장소 / 지식 저장소**로 사용하고 싶음
- 논문은 레이아웃 보존 번역, 세미나 자료/외부 문서는 **탐색 가능한 형태**로 저장
- 향후 **챗봇 연계**를 통한 개인 지식 도우미 활용 기대
- 외부 인터넷 서비스(NotebookLM, Notion)와 유사한 경험 기대

**팀장 방향:**
- **NotebookLM + Obsidian의 폐쇄망 버전** — 두 서비스의 핵심 기능 중 현업에 실질적 도움이 되는 기능을 조합
- Obsidian의 지식 그래프, NotebookLM의 AI 문서 이해를 폐쇄망 환경에서 구현
- 최종적으로 번역·챗봇·지식 관리가 하나의 시스템에서 동작

### 3.4 차별적 가치 — 왜 이 플랫폼인가

NotebookLM과 Obsidian은 각각 강력한 도구이지만, 다음을 **모두 충족하는 제품은 시장에 없다**:

| 요구사항 | NotebookLM | Obsidian | **본 플랫폼** |
|----------|:----------:|:--------:|:------------:|
| 폐쇄망(에어갭) 동작 | ❌ (Google Cloud) | ⚠️ (앱은 로컬, AI 플러그인은 클라우드) | ✅ |
| 외국어 PDF 번역 | ❌ | ❌ | ✅ |
| AI 문서 이해/챗봇 | ✅ | ⚠️ (플러그인) | ✅ (Ollama) |
| 로컬 문서 저장 | ❌ (클라우드) | ✅ | ✅ |
| 도메인 용어집 | ❌ | ❌ | ✅ |
| 기술문서 특화 (수식, 표, 규격) | ❌ | ❌ | ✅ |

### 3.5 업계 트렌드 (2024~2026)

| 트렌드 | 시사점 |
|--------|--------|
| 문서 관리 → 지식 플랫폼 전환 | 2026년까지 기업 80%가 생성형 AI 배포 전망 |
| RAG + Agentic Parsing 표준화 | 조직 문서 기반 AI 응답 생성이 엔터프라이즈 표준 |
| PDF → Markdown 전환 | Marker(GitHub 14k+), Docling(IBM) 등 PDF→MD 도구 급부상 |
| Markdown 기반 지식 관리 | Obsidian, Logseq, Notion — 모두 Markdown 기반. 편집·검색·연결에 최적 |
| 폐쇄망 AI | 전체 파이프라인(LLM + 임베딩 + 벡터DB)의 에어갭 운영 필요 |
| MBSE + Digital Thread | 방산 분야 규격 관리 현대화의 핵심 축 |
| Vanilla JS 재부상 (2025) | Netflix: React→Vanilla JS 전환 사례. 네이티브 API 발전으로 실용성 재확인 |

### 4.3 Markdown 전략 — 왜 HTML이 아닌 Markdown인가

번역 결과의 저장 포맷으로 HTML 대신 **Markdown**을 선택한다.

| 관점 | HTML 직접 생성 | Markdown 저장 → HTML 렌더링 |
|------|---------------|---------------------------|
| 생성 난이도 | 태그 중첩, 스타일 속성 관리 | `#`, `**`, `- ` 등 단순 문법 |
| 편집 가능성 | 사용자가 HTML 편집은 비현실적 | 텍스트 에디터로 누구나 수정 가능 |
| 외부 활용 | 브라우저에서만 열림 | Obsidian, Typora, VS Code 등 호환 |
| RAG 연계 | HTML 파싱 필요 | 텍스트 추출 거의 불필요 |
| 지식 저장소 | 플랫폼 종속 | 사용자가 .md 파일을 가져갈 수 있음 |
| 버전 관리 | diff가 태그로 오염 | 깔끔한 텍스트 diff |

**적용 범위**: Translator의 번역 결과 웹 뷰에만 Markdown 적용. Explorer의 DOCX→HTML 변환은 복잡한 서식(병합 표, MathML 수식, 이미지 크기 제어)이 필요하므로 HTML 유지.

```
Explorer: Word → HTML (유지) — 복잡한 서식의 확정 기술문서 열람
Translator: PDF 번역 → Markdown (신규) — 번역 결과의 편집·활용·지식화
```

## 5. 기술 기반 전략

### 5.1 핵심 결정

| 결정 | 근거 |
|------|------|
| **Vanilla JS 유지** | 1개월 만에 3개 시스템을 구현한 생산성. Netflix도 React→Vanilla JS 전환. "세련된 느낌"은 프레임워크가 아닌 디자인이 결정. 폐쇄망에서 빌드 없는 배포의 단순함 |
| **K-Spec은 React + Vite** | K-Spec은 별도 시스템으로 시작. 승인 워크플로우/Spec Tree 등 복잡한 상태 관리에 적합. 내부 도구에 Next.js는 과잉 (SEO 불필요) |
| **백엔드 FastAPI 통일** | 현재 플랫폼과 K-Spec 모두 FastAPI. 문서 분석 서비스도 FastAPI로 구축 가능 |
| **SQLite 유지, PostgreSQL은 K-Spec 도입 시** | 현재 규모(수십 명)에서 SQLite 충분. K-Spec의 Spec Tree/버전관리/워크플로우에서 PostgreSQL 필요 |
| **Big Bang 재작성 금지** | 엔터프라이즈 마이그레이션의 75%가 실패. Strangler Fig 패턴(점진적 교체)이 업계 표준 |

### 5.2 기술 스택 로드맵

```
현재 (2026 Q1)
  Frontend: Vanilla JS + CSS 디자인 시스템
  Backend:  FastAPI (단일)
  DB:       SQLite + JSON 파일
  AI:       Ollama + FAISS + bge-m3

K-Spec 시작 시 (2026 H2 예상)
  K-Spec Frontend: React + Vite
  K-Spec Backend:  FastAPI + Celery + Redis
  K-Spec DB:       PostgreSQL + Elasticsearch
  배포:            Docker Compose
  * 현재 플랫폼은 변경 없이 유지

공통 서비스 분리 시 (K-Spec 검증 후)
  문서 분석 서비스: 독립 FastAPI (port 8010)
  → 현재 플랫폼과 K-Spec 모두 HTTP API로 호출

장기 (실사용 데이터 축적 후)
  현재 플랫폼의 신규 기능을 React 모듈로 추가 (Strangler Fig)
  Vanilla JS 페이지를 필요에 따라 하나씩 전환
  두 시스템의 UI 통합 검토
```

### 5.3 왜 지금 React로 전환하지 않는가

1. **작동하는 코드를 버리는 비용** — 3개 시스템이 1개월 만에 완성, React 재작성 시 동일 기간에 절반도 불가
2. **사용자 가치 제로** — 프레임워크 전환은 사용자에게 아무 변화 없음
3. **빌드 시스템 의존성** — React는 번들러(Vite 등) 필수, 폐쇄망 배포 복잡도 증가
4. **Netflix 사례** — 오히려 React에서 Vanilla JS로 전환 (프레임워크 오버헤드 제거)
5. **"세련된 느낌"의 실체** — CSS 트랜지션, 타이포그래피, 여백, 애니메이션이 결정. 이미 디자인 시스템(tokens.css + components.css) 보유

## 7. K-Spec 연계 전략

### 7.1 K-Spec 개요

K-Spec은 KAI의 표준 기술문서(규격서/스펙) 체계를 수립하는 **별도 시스템**이다.

- **Mother Spec**: 기존 분산 스펙을 통합한 표준
- **Branch Spec**: Mother에서 사업별/용도별 파생
- **Spec Tree**: 전체 스펙의 계층 관계 (L0→L1→L2→L3)

상세 설계: `docs/architecture-context.md`, `docs/K-Spec_Proposal_v0.3.docx` 참조.

### 7.2 현재 플랫폼과의 관계

| 현재 플랫폼 | K-Spec |
|------------|--------|
| **개인 엔지니어 도구** | **팀/조직 관리 시스템** |
| Vanilla JS, 파일 기반 | React + PostgreSQL + Docker |
| 번역, 탐색, 비교 | 규격 제정, 승인 워크플로우, 대시보드 |
| 운영 준비 중 | 미착수 (PoC 예정) |

**핵심 결정**: 별도 시스템으로 시작하고, **문서 분석 서비스 API로 연결**한다.

### 7.3 문서 분석 서비스 (공통 레이어)

```
┌── 현재 플랫폼 ──┐     ┌── K-Spec ──┐
│ Explorer        │     │ Spec Tree  │
│ Compare    ─────┼──┐  │ 워크플로우  │
│ Translator      │  │  │ 대시보드   │
└─────────────────┘  │  └─────┬──────┘
                     │        │
                     ▼        ▼
              ┌─────────────────────┐
              │  문서 분석 서비스     │
              │  (독립 FastAPI)      │
              │                     │
              │  문서 구조 파싱      │
              │  도메인 용어 추출    │
              │  문장 유사도 분석    │
              │  작성 규칙 검증     │
              └─────────────────────┘
```

**분리 시점**: Compare와 K-Spec이 **실제로 같은 기능을 호출하는 시점**. 지금은 YAGNI — 추상화가 이르면 실제 요구와 안 맞는 API가 만들어진다.

### 7.4 접점

| 접점 | 현재 플랫폼 측 | K-Spec 측 |
|------|--------------|-----------|
| 문서 비교 | Compare 서브시스템 | 기존 스펙 간 중복/차이 탐지 (ADR-004) |
| 용어 관리 | Explorer 용어 사전 (참조용) + Translator 용어집 (번역 제어) | 도메인 용어 자동 추출 + 사용자 사전 |
| 규칙 검증 | Compare 6종 규칙 | KAI 작성 지침 기반 검증 |

## 9. 설계 원칙

### 9.1 실패하지 않는 시스템을 위한 5원칙

엔터프라이즈 마이그레이션 실패 사례에서 추출한 원칙:

| # | 원칙 | 적용 |
|---|------|------|
| 1 | **한 번에 하나만 바꿔라** (Strangler Fig) | Plan 16을 먼저 완성, K-Spec은 별도 시작 |
| 2 | **작동하는 것을 증명하고 확장해라** | K-Spec PoC에서 샘플 3~5개로 먼저 검증 |
| 3 | **공통 레이어는 필요할 때 분리해라** | 문서 분석 서비스는 실제 중복 호출이 발생할 때 |
| 4 | **매 단계에서 사용자 가치를 전달해라** | 각 Phase 완료 시 체감 가능한 변화 |
| 5 | **기술 결정은 조직 구조를 따라가라** | 개인 도구(현재)와 팀 시스템(K-Spec)은 별도 |

### 9.2 기술 원칙

- **Vanilla JS only** — 프레임워크/라이브러리 금지 (현재 플랫폼)
- **모놀리식 HTML** — 각 서브시스템은 단일 HTML 파일
- **빌드 시스템 없음** — 번들러, 트랜스파일러 미사용
- **업계 표준 방식 우선** — 검증된 패턴/도구 채택
- **과잉 설계 금지** — 현재 규모에서 필요한 것만 구현

### 9.3 디자인 시스템

CSS 토큰 기반 디자인 시스템이 전 서브시스템에 적용됨:
- `css/tokens.css` — 색상, 간격, 둥글기, 트랜지션 변수
- `css/components.css` — 버튼, 입력, 배지, 스피너 등 공통 컴포넌트
- `css/modal.css` — 모달 패턴
- 다크모드 완전 지원
- 상세: `memory/theme-guide.md`

## 10. 구조적 리스크 및 대응

### 10.1 현재 구조의 강점

1. **빠른 개발 속도** — 1개월 만에 3개 시스템 완성
2. **모듈화된 백엔드** — FastAPI 라우터 기반, 모듈 추가가 파일 하나 수준
3. **폐쇄망 완전 호환** — 외부 CDN/SaaS 의존 없음
4. **런타임 설정** — 재배포 없이 운영 환경 조정
5. **AI 파이프라인 확립** — RAG + 번역 + 비교 분류가 동일 Ollama 인프라 공유

### 10.2 리스크 및 대응

| 리스크 | 현재 상태 | 대응 |
|--------|----------|------|
| JS 파일 비대화 | translator.js 2700줄, compare.html 3000줄 | 외부 JS 파일 분리 패턴 확대 |
| PDF DRM | 번역 PDF가 시간 경과 후 잠김 | Plan 16 Phase 4 다운로드 + Phase 5 Markdown으로 대응 |
| 파일 기반 동시 쓰기 | JSON 파일 동시 수정 시 충돌 가능 | 현재 규모에서는 낮은 위험. 사용자 증가 시 SQLite 확장 |
| 단일 인스턴스 | 하나의 문서 컬렉션만 운영 | 멀티 프로젝트는 K-Spec 단계에서 고려 |
| 지식 플랫폼 범위 확대 | NotebookLM/Obsidian 전체 재현 시도 위험 | 핵심 가치(챗봇 + Markdown + 링크)에 집중, 주변 기능은 실사용 피드백 후 |

### 10.3 재설계가 필요해지는 시점

- 동시 사용자 50명+ → DB 기반 세션/큐 필요
- 문서 수 1,000개+ → 파일 기반 → DB 전환 검토
- K-Spec 통합 시 → 공통 서비스 분리, 인증 체계 통합

**현재 규모에서는 재설계 불필요. 과잉 설계가 더 큰 리스크.**
