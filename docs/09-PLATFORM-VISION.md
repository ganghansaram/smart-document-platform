## 1. 프로젝트 개요

### 1.1 발전 경과

본 프로젝트는 "KF-21 개발 백서 열람용 웹북" 시범 시스템으로 시작하여, 약 1개월 만에 기술 문서 활용 플랫폼으로 확장되었다.

```
Phase 1 (완료)  : 정적 웹북               → "읽는 시스템"
Phase 2 (완료)  : RAG + 편집기            → "활용하는 시스템"
Phase 3 (완료)  : 관리 기능 + 통계         → "운영하는 시스템"
Phase 4 (완료)  : 비교/번역/다중 시스템     → "기술 문서 활용 플랫폼"
Phase 5 (완료)  : 품질 향상 + 지식 저장소   → "지식 활용 플랫폼"
Phase 6 (완료)  : 디자인 시스템 리파인먼트   → "세련된 플랫폼"
Phase 7 (진행중) : 비교/검증 고도화 + 전략   → "실무 검증 플랫폼"
```

### 1.2 핵심 제약

- **에어갭 환경**: 외부 인터넷 차단, 모든 구성요소 자체 호스팅
- **Vanilla JS + 모놀리식 HTML**: 프레임워크/빌드 시스템 없음
- **사용자**: 설계/품질/공정 엔지니어 (비개발직군)
- **PDF DRM**: 사내 PDF는 일정 시간 후 DRM 적용 → 번역 결과 다운로드 필수

## 3. 궁극적 목표

### 3.1 비전

> **"폐쇄망 엔지니어를 위한 지식 플랫폼 — 읽고, 이해하고, 검증하고, 만든다"**
>
> NotebookLM의 AI 문서 이해 + Obsidian의 로컬 지식 관리를 결합하되,
> **폐쇄망 동작**, **외국어 기술문서 번역**, **구조화 문서 합성**이라는 경쟁 제품에 없는 차별점을 갖는다.
>
> 4개 시스템이 사용자의 행위 단계를 커버한다:
> **Explorer**(소비) → **Notebook**(내재화) → **Verify**(검증) → **Author**(생산)

### 3.2 현재 → 목표

| 시스템 | 현재 | 목표 | 달성도 |
|--------|------|------|:------:|
| **Explorer** | 문서 탐색 + RAG + AI 챗봇 | **지식 허브** — 조직 문서 탐색/검색/AI 질의 | ✅ 완료 |
| **Notebook** | PDF 번역 + 요약/Q&A/마인드맵/편집 | **개인 지식 저장소** — 번역 + Markdown + 챗봇 + 문서 분석 | ✅ 완료 |
| **Verify** | 문서 비교 + 규칙 검증 + AI 분류 | **문서 품질 게이트** — 비교 + 유사도 검사 + 규칙 검증 | 🔨 고도화 중 |
| **Author** | (없음) | **구조화 문서 합성** — 다중 소스 분석 → 비교 매트릭스 → 초안 생성 | ⏳ 미착수 |
| *(외부)* | *(없음)* | *K-Spec — 표준 규격 관리 (플랫폼 외부 시스템, API 연계)* | *⏳ 별도* |

### 3.3 사용자 피드백 및 경영층 방향

**테스트 참여 동료들의 요청:**
- Translator를 **개인 문서 저장소 / 지식 저장소**로 사용하고 싶음
- 논문은 레이아웃 보존 번역, 세미나 자료/외부 문서는 **탐색 가능한 형태**로 저장
- 향후 **챗봇 연계**를 통한 개인 지식 도우미 활용 기대
- 외부 인터넷 서비스(NotebookLM, Notion)와 유사한 경험 기대

**팀장 방향:**
- **NotebookLM + Obsidian의 폐쇄망 버전** — 두 서비스의 핵심 기능 중 현업에 실질적 도움이 되는 기능을 조합
- Obsidian의 지식 그래프, NotebookLM의 AI 문서 이해를 폐쇄망 환경에서 구현
- 최종적으로 번역·챗봇·지식 관리가 하나의 시스템에서 동작

### 3.4 차별적 가치 — 왜 이 플랫폼인가

NotebookLM과 Obsidian은 각각 강력한 도구이지만, 다음을 **모두 충족하는 제품은 시장에 없다**:

| 요구사항 | NotebookLM | Obsidian | **본 플랫폼** |
|----------|:----------:|:--------:|:------------:|
| 폐쇄망(에어갭) 동작 | ❌ (Google Cloud) | ⚠️ (앱은 로컬, AI 플러그인은 클라우드) | ✅ |
| 외국어 PDF 번역 | ❌ | ❌ | ✅ |
| AI 문서 이해/챗봇 | ✅ | ⚠️ (플러그인) | ✅ (Ollama) |
| 로컬 문서 저장 | ❌ (클라우드) | ✅ | ✅ |
| 도메인 용어집 | ❌ | ❌ | ✅ |
| 기술문서 특화 (수식, 표, 규격) | ❌ | ❌ | ✅ |
| **다중 문서 구조화 합성** | ❌ | ❌ | ✅ (Author) |
| **크로스링구얼 유사도 검사** | ❌ | ❌ | ✅ (Verify) |

### 3.5 업계 트렌드 (2024~2026)

| 트렌드 | 시사점 |
|--------|--------|
| 문서 관리 → 지식 플랫폼 전환 | 2026년까지 기업 80%가 생성형 AI 배포 전망 |
| RAG + Agentic Parsing 표준화 | 조직 문서 기반 AI 응답 생성이 엔터프라이즈 표준 |
| PDF → Markdown 전환 | Marker(GitHub 14k+), Docling(IBM) 등 PDF→MD 도구 급부상 |
| Markdown 기반 지식 관리 | Obsidian, Logseq, Notion — 모두 Markdown 기반. 편집·검색·연결에 최적 |
| 폐쇄망 AI | 전체 파이프라인(LLM + 임베딩 + 벡터DB)의 에어갭 운영 필요 |
| MBSE + Digital Thread | 방산 분야 규격 관리 현대화의 핵심 축 |
| Vanilla JS 재부상 (2025) | Netflix: React→Vanilla JS 전환 사례. 네이티브 API 발전으로 실용성 재확인 |
| **Agentic Document Processing** | 단순 RAG를 넘어 에이전트가 문서를 읽고 판단/행동. 스펙 초안 생성에 직접 적용 가능 |
| **Compliance-as-Code** | 작성 규칙을 코드화하여 CI/CD처럼 문서 작성 시 자동 검증. Compare 규칙 검증이 이 방향의 씨앗 |
| **Cross-lingual Similarity** | 다국어 임베딩(bge-m3 등)으로 한↔영 의미 유사도 비교가 실용 수준 도달. 스펙 표절 검사에 핵심 |

## 4. 지식 플랫폼 기능 로드맵

### 4.1 참조 제품 기능 분석

NotebookLM과 Obsidian의 핵심 기능을 분석하고, 폐쇄망 환경에서의 구현 가능성과 현업 가치를 평가한다.

#### NotebookLM (Google) — AI 기반 문서 연구 도우미

| 기능 | 설명 | 구현 | 비고 |
|------|------|:----:|------|
| 문서 업로드 | PDF, 문서 등을 소스로 등록 | ✅ | 이미 있음 (Translator 업로드) |
| AI 채팅 (문서 기반) | 업로드한 문서 기반 질의응답 | ✅ | Explorer RAG 재활용 (Ollama + FAISS) |
| 소스 근거 인용 | 답변에 출처 문단을 인용·하이라이트 | ✅ | Explorer에 이미 있음 (섹션 네비게이션) |
| 요약 생성 | 문서별 자동 요약, 브리핑 문서 | ✅ | Ollama 프롬프트로 구현 가능 |
| 커스텀 지시 | 톤, 길이, 형식 지정 | ✅ | 시스템 프롬프트 설정 |
| 다국어 출력 | 응답 언어 선택 | ✅ | Ollama 프롬프트로 가능 |
| 퀴즈/플래시카드 | 학습용 퀴즈 자동 생성 | ✅ | Ollama 프롬프트로 구현 가능 |

### 4.3 Markdown 전략 — 왜 HTML이 아닌 Markdown인가

번역 결과의 저장 포맷으로 HTML 대신 **Markdown**을 선택한다.

| 관점 | HTML 직접 생성 | Markdown 저장 → HTML 렌더링 |
|------|---------------|---------------------------|
| 생성 난이도 | 태그 중첩, 스타일 속성 관리 | `#`, `**`, `- ` 등 단순 문법 |
| 편집 가능성 | 사용자가 HTML 편집은 비현실적 | 텍스트 에디터로 누구나 수정 가능 |
| 외부 활용 | 브라우저에서만 열림 | Obsidian, Typora, VS Code 등 호환 |
| RAG 연계 | HTML 파싱 필요 | 텍스트 추출 거의 불필요 |
| 지식 저장소 | 플랫폼 종속 | 사용자가 .md 파일을 가져갈 수 있음 |
| 버전 관리 | diff가 태그로 오염 | 깔끔한 텍스트 diff |

**적용 범위**: Translator의 번역 결과 웹 뷰에만 Markdown 적용. Explorer의 DOCX→HTML 변환은 복잡한 서식(병합 표, MathML 수식, 이미지 크기 제어)이 필요하므로 HTML 유지.

```
Explorer:  Word → HTML     — 복잡한 서식의 확정 기술문서 열람 (읽기 전용)
Notebook:  PDF → Markdown  — 번역 결과의 편집·활용·지식화
Author:    소스 → Markdown — 다중 문서 합성 초안 생성·편집
Verify:    텍스트 추출      — 비교/유사도 내부 처리 (사용자 편집 없음)
```

**Markdown이 플랫폼의 공용 포맷(lingua franca)**: 시스템 간 데이터 전달 시 변환 불필요. Notebook에서 분석한 문서를 Author의 소스로, Author에서 생성한 초안을 Verify로 보낼 때 모두 `.md` 그대로 흐른다.

## 5. 기술 기반 전략

### 5.1 핵심 결정

| 결정 | 근거 |
|------|------|
| **Vanilla JS 유지** | 1개월 만에 3개 시스템을 구현한 생산성. Netflix도 React→Vanilla JS 전환. "세련된 느낌"은 프레임워크가 아닌 디자인이 결정. 폐쇄망에서 빌드 없는 배포의 단순함 |
| **Author도 Vanilla JS** | 4개 시스템 모두 동일 기술 스택. Author의 비교 매트릭스/편집기도 기존 컴포넌트(editor-core.js, 테이블 UI) 재활용 |
| **K-Spec은 플랫폼 외부** | K-Spec은 특정 부서의 규격 관리 도구로, 범용 지식 플랫폼과 성격이 다름. 필요 시 API 연계하되 플랫폼 안에 넣지 않음 |
| **백엔드 FastAPI 통일** | 4개 시스템 모두 동일 FastAPI 백엔드. 라우터 추가로 시스템 확장 |
| **SQLite + JSON 유지** | 현재 규모(수십 명)에서 충분. 문서 1,000개+ 시 DB 전환 검토 |
| **Markdown이 공용 포맷** | 시스템 간 데이터 교환 포맷. Notebook 편집, Author 초안, Verify 입력 모두 MD 기준 |
| **Big Bang 재작성 금지** | 엔터프라이즈 마이그레이션의 75%가 실패. Strangler Fig 패턴(점진적 교체)이 업계 표준 |

### 5.2 기술 스택 로드맵

```
현재 (2026 Q2)
  Frontend: Vanilla JS + CSS 디자인 시스템 (4개 시스템 통일)
  Backend:  FastAPI (단일, 라우터 기반 확장)
  DB:       SQLite + JSON 파일
  AI:       Ollama + FAISS + bge-m3
  포맷:     Markdown (시스템 간 공용)

Verify + Author 추가 시 (2026 Q2~Q3)
  verify.html, author.html 추가 (기존 패턴 동일)
  backend/api/verify.py, backend/api/author.py 라우터 추가
  기존 서비스 레이어 재활용 (임베딩, 텍스트 추출, Ollama)

장기 — 공통 서비스 분리 (실제 중복 호출 발생 시)
  문서 분석 서비스: 독립 FastAPI (port 8010)
  → 플랫폼 내부 시스템 + 외부 시스템(K-Spec 등) 모두 호출 가능
```

### 5.3 왜 지금 React로 전환하지 않는가

1. **작동하는 코드를 버리는 비용** — 3개 시스템이 1개월 만에 완성, React 재작성 시 동일 기간에 절반도 불가
2. **사용자 가치 제로** — 프레임워크 전환은 사용자에게 아무 변화 없음
3. **빌드 시스템 의존성** — React는 번들러(Vite 등) 필수, 폐쇄망 배포 복잡도 증가
4. **Netflix 사례** — 오히려 React에서 Vanilla JS로 전환 (프레임워크 오버헤드 제거)
5. **"세련된 느낌"의 실체** — CSS 트랜지션, 타이포그래피, 여백, 애니메이션이 결정. 이미 디자인 시스템(tokens.css + components.css) 보유

## 7. 외부 연계 — K-Spec

### 7.1 위상 재정의

K-Spec(표준 규격 관리 시스템)은 **플랫폼 외부의 별도 시스템**으로 분류한다.

| 관점 | Smart Document Platform | K-Spec |
|------|------------------------|--------|
| 성격 | **범용 지식 플랫폼** — 모든 엔지니어가 사용 | **부서 업무 도구** — 특정 팀의 규격 관리 |
| 사용자 | 설계/품질/공정 엔지니어 전체 | 재료공정팀/공정개발팀 |
| 기술 | Vanilla JS, 파일 기반, 경량 | React + PostgreSQL + Docker (예상) |
| 관계 | API를 **제공**하는 측 | API를 **소비**하는 측 |

**핵심 결정**: K-Spec이 필요로 하는 문서 분석 기능(유사도, 규칙 검증, 텍스트 추출)은 이미 Verify/Author에 구현된다. K-Spec은 이 API를 호출하는 외부 클라이언트.

### 7.2 연계 구조

```
┌─── Smart Document Platform ──────────────────────────┐
│                                                      │
│  Explorer · Notebook · Verify · Author               │
│       │          │         │         │               │
│       ▼          ▼         ▼         ▼               │
│  ┌─────────────────────────────────────────────┐     │
│  │  공통 서비스 레이어 (향후 독립 분리 가능)      │     │
│  │  텍스트 추출 · 임베딩 · 유사도 · 규칙 검증    │     │
│  └───────────────────┬─────────────────────────┘     │
└──────────────────────┼───────────────────────────────┘
                       │ REST API
                       ▼
              ┌─ K-Spec (외부) ─┐
              │  Spec Tree      │
              │  승인 워크플로우  │
              │  대시보드        │
              └─────────────────┘
```

**분리 시점**: Verify/Author 내부에 구현한 서비스 로직을 독립 FastAPI로 분리하는 것은, K-Spec이 **실제로 같은 기능을 호출하는 시점**에 한다 (YAGNI).

### 7.3 K-Spec이 활용할 플랫폼 API

| 플랫폼 기능 | K-Spec 활용 |
|------------|-------------|
| 유사도 검사 (Verify) | Mother Spec 제정 시 원문 표절 점검 |
| 규칙 검증 (Verify) | KAI 작성 지침 준수 자동 검증 |
| 구조화 추출 (Author) | 기존 스펙에서 요구사항 자동 추출 |
| 비교 매트릭스 (Author) | 기존 유사 스펙 통합 분석 |

상세 설계: `docs/architecture-context.md`, `docs/K-Spec_Proposal_v0.3.docx` 참조.

## 9. 설계 원칙

### 9.1 실패하지 않는 시스템을 위한 5원칙

엔터프라이즈 마이그레이션 실패 사례에서 추출한 원칙:

| # | 원칙 | 적용 |
|---|------|------|
| 1 | **한 번에 하나만 바꿔라** (Strangler Fig) | Verify 먼저 완성, Author는 Verify 검증 후 |
| 2 | **작동하는 것을 증명하고 확장해라** | Author MVP로 비교 매트릭스 핵심 가치 먼저 검증 |
| 3 | **공통 레이어는 필요할 때 분리해라** | 문서 분석 서비스는 실제 외부 호출이 발생할 때 |
| 4 | **매 단계에서 사용자 가치를 전달해라** | 각 Phase 완료 시 체감 가능한 변화 |
| 5 | **범용 플랫폼과 부서 도구를 분리해라** | K-Spec(부서 도구)은 플랫폼 외부, API 연계만 |

### 9.2 기술 원칙

- **Vanilla JS only** — 프레임워크/라이브러리 금지 (현재 플랫폼)
- **모놀리식 HTML** — 각 서브시스템은 단일 HTML 파일
- **빌드 시스템 없음** — 번들러, 트랜스파일러 미사용
- **업계 표준 방식 우선** — 검증된 패턴/도구 채택
- **과잉 설계 금지** — 현재 규모에서 필요한 것만 구현

### 9.3 디자인 시스템

CSS 토큰 기반 디자인 시스템이 전 서브시스템에 적용됨:
- `css/tokens.css` — 색상, 간격, 둥글기, 트랜지션 변수
- `css/components.css` — 버튼, 입력, 배지, 스피너 등 공통 컴포넌트
- `css/modal.css` — 모달 패턴
- 다크모드 완전 지원
- 상세: `memory/theme-guide.md`

## 10. 구조적 리스크 및 대응

### 10.1 현재 구조의 강점

1. **빠른 개발 속도** — 1개월 만에 3개 시스템 완성
2. **모듈화된 백엔드** — FastAPI 라우터 기반, 모듈 추가가 파일 하나 수준
3. **폐쇄망 완전 호환** — 외부 CDN/SaaS 의존 없음
4. **런타임 설정** — 재배포 없이 운영 환경 조정
5. **AI 파이프라인 확립** — RAG + 번역 + 비교 분류가 동일 Ollama 인프라 공유

### 10.2 리스크 및 대응

| 리스크 | 현재 상태 | 대응 |
|--------|----------|------|
| JS 파일 비대화 | translator.js ~5000줄, compare.html ~3500줄 | 외부 JS 파일 분리 패턴 확대 (editor-core.js, toast.js 등 이미 진행 중) |
| PDF DRM | 번역 PDF가 시간 경과 후 잠김 | Plan 16 Phase 4 다운로드 + Phase 5 Markdown으로 대응 |
| 파일 기반 동시 쓰기 | JSON 파일 동시 수정 시 충돌 가능 | 현재 규모에서는 낮은 위험. 사용자 증가 시 SQLite 확장 |
| 단일 인스턴스 | 하나의 문서 컬렉션만 운영 | Author 프로젝트 기반으로 부분 해소, 멀티 테넌트는 장기 과제 |
| 지식 플랫폼 범위 확대 | NotebookLM/Obsidian 전체 재현 시도 위험 | 핵심 가치(챗봇 + Markdown + 링크)에 집중, 주변 기능은 실사용 피드백 후 |

### 10.3 재설계가 필요해지는 시점

- 동시 사용자 50명+ → DB 기반 세션/큐 필요
- 문서 수 1,000개+ → 파일 기반 → DB 전환 검토
- 외부 시스템 연계 시 → 공통 서비스 분리

**현재 규모에서는 재설계 불필요. 과잉 설계가 더 큰 리스크.**

## 11. 플랫폼 확장 전략

### 11.1 4체제 아키텍처

Phase A~A+ 완료로 지식 플랫폼의 기반이 갖춰졌다. 플랫폼은 **사용자 행위 단계**에 따른 4개 시스템으로 구성한다:

| 시스템 | 행위 | 핵심 기능 | 상태 |
|--------|------|----------|:----:|
| **Explorer** | 소비 (읽기) | 조직 문서 탐색, RAG 검색, AI 질의 | ✅ |
| **Notebook** | 내재화 (이해) | 개인 문서 번역, 분석, 지식 관리 | ✅ |
| **Verify** | 검증 (판단) | 문서 비교, 유사도 검사, 규칙 검증 | 🔨 |
| **Author** | 생산 (창작) | 다중 소스 분석, 비교 매트릭스, 초안 생성 | ⏳ |

### 11.2 시스템 간 데이터 흐름

```
외부 스펙 입수 ──→ Notebook (번역/분석/이해)
                      │
                      ├──→ Explorer (RAG 인덱스 등록, 검색 가능)
                      │
                      └──→ Author (소스 문서로 투입)
                              │
                              ├── 구조화 추출 (AI)
                              ├── 비교 매트릭스 (공통/충돌/단일)
                              ├── 선별 + 편집 (사람이 판단)
                              ├── 초안 생성 (Markdown)
                              │
                              └──→ Verify (유사도 검사, 규칙 검증)
                                      │
                                      └──→ Author (피드백 반영, 수정)
                                              │
                                              └──→ 최종 Markdown 다운로드
```

**공용 포맷**: 시스템 간 모든 텍스트 데이터는 **Markdown**으로 흐른다.

### 11.3 확장 방향 — 3개 축

#### 축 1: Verify 고도화 (즉시 착수)

사용자 요청이 발생하고 있으므로 즉시 대응.

| 기능 | 목적 | 계획 |
|------|------|------|
| 유사도 검사 모드 | 외부 원문 대비 표절/유사 구간 식별 (한↔영 크로스링구얼) | Plan-23 Phase 1 |
| 내보내기 확장 | 공식 검토 리포트 (Excel/HTML) | Plan-23 Phase 2 |
| 요구사항 문장 분류 | shall/should/may 자동 분류 | Plan-23 Phase 3 |

#### 축 2: Author 시스템 구축 (Verify 검증 후)

시장에 없는 "구조화 문서 합성" 기능으로 핵심 차별화.

| Phase | 기능 | 사용자 가치 |
|-------|------|-----------|
| MVP | 소스 2~3개 → AI 비교 테이블 → 체크 → MD 초안 | 엑셀 3시간 → 30분 |
| v2 | 커스텀 템플릿, 메모/코멘트, 편집기 | 반복 사용 |
| v3 | Verify/Notebook 연계 | 워크플로우 완성 |

#### 축 3: 데이터 관리 기준 (병행 정립)

코드가 아니라 원칙. 4체제 확장 전에 확립.

| 기준 | 내용 |
|------|------|
| **문서 ID 체계** | 4개 시스템 간 교차 참조 가능한 통일 ID |
| **메타데이터 스키마** | 공통 필드 (title, created_at, author, tags, format) 표준화 |
| **저장 현황** | Explorer: SQLite+HTML, Notebook: JSON+PDF+MD, Verify: 무상태, Author: JSON+MD(프로젝트별) |
| **전환 기준** | 문서 1,000개+ → DB 전환, 동시 사용자 50명+ → DB 세션/큐 |

### 11.4 실행 순서

```
[즉시]  Verify 고도화 (Plan-23)        ←── 사용자 요청 대응
[병행]  데이터 관리 기준 수립            ←── 아키텍처 원칙 확립
[병행]  Compare → Verify 리브랜딩       ←── 런처/헤더 명칭 변경
  ↓

  ↓
[Q3]   Author v2 + Verify/Notebook 연계 ←── 시스템 간 데이터 흐름
  ↓
[필요시] 공통 서비스 분리               ←── 외부 시스템(K-Spec 등) 연계 시
```
